# 领域建模（嵌入式）

积极构建和锐化项目的领域模型。这是*主动*的纪律——挑战术语、发明边界场景、与数据手册和代码交叉验证、在术语和决策确定时立即写入词汇表和 ADR。

## 文件结构

单上下文（大多数仓库）：

```
/
├── CONTEXT.md
├── PROJECT-KNOWLEDGE-GRAPH.md    ← 来自 scan-embedded-project
├── docs/
│   └── adr/
│       ├── 0001-<决策简称>.md
│       └── 0002-<决策简称>.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则仓库有多个子上下文——每个子项目有自己的 `CONTEXT.md` 和 `docs/adr/`。

按需创建文件——只有当有内容可写时才创建。

## 嵌入式术语模式

### 模式 1：厂商间同名不同义

同一名字在不同厂商 SDK 中有不同含义：

```
"GPIO_PIN_RESET"：
├── STM32 HAL：  GPIO_PIN_RESET = 引脚输出低电平
├── ESP-IDF：    gpio_reset_pin() = 将引脚恢复到默认状态（不是输出电平！）
├── nRF5 SDK：    引脚复位 = 复位引脚配置寄存器
└── 通用：        "reset" 指硬件复位线还是软件复位？

→ CONTEXT.md 条目：精确定义本项目使用的含义，标注厂商
```

当工程集成多个厂商 SDK 时，标记每个过载术语。

### 模式 2：同一芯片内术语过载

一个词在同一 MCU 中有多种含义：

```
"channel"（通道）：
├── DMA 通道        （数据传输管道）
├── ADC 通道        （模拟输入多路复用器）
├── 定时器通道      （PWM 输出或输入捕获）
├── RF 通道         （无线频点，如 2.4GHz 信道 11-26）
└── 应用通道        （如 BLE GATT 特征值）

→ 永远不要单独使用"通道"——始终加前缀：dma_通道、adc_通道、rf_通道
```

### 模式 3：硬件 vs 软件视角

```
"中断"：
├── 硬件视角：IRQ #27，优先级 0-15，边沿触发，NVIC 使能位
└── 软件视角：ISR 函数名，延迟处理任务，事件标志

→ CONTEXT.md：硬件用 irq_N，软件处理函数用 isr_<名称>
```

### 模式 4：协议栈术语层级

协议术语有嵌套——每层需要自己的词汇表条目：

```
Zigbee 中的"地址"：
├── IEEE 地址   （64 位，全球唯一，出厂分配）
├── NWK 地址    （16 位，入网时动态分配）
├── Endpoint    （8 位，应用入口点）
├── Cluster ID  （16 位，功能分组）
├── PAN ID      （16 位，网络标识符）
└── 短地址      （NWK 地址的别名——推荐使用 NWK 地址以保持精确）
```

## 会话期间

### 对照词汇表挑战

当用户使用的术语与 `CONTEXT.md` 冲突时："你的词汇表将'binding'定义为直接源到目的地的配对，但你似乎指的是通过协调器的间接绑定——是哪个？"

### 锐化模糊语言

当用户使用模糊术语时，提出精确的替代：

```
用户说"无线"
→ "哪一层？PHY（实际收发器）/ MAC（帧处理）/ NWK（路由逻辑）？"
→ CONTEXT.md：三层都定义，解决后永远不允许裸用"无线"
```

### 讨论具体场景

用具体的硬件场景对术语进行压力测试：

```
"休眠模式"：
├── "如果设备在休眠模式中，GPIO 中断触发，
│   ISR 是立即运行还是等唤醒稳定后？"
├── "如果在休眠时 UART RX 启动，第一个字节会丢失还是被缓冲？"
└── "'休眠'是指仅 CPU 停止，还是整个芯片断电？"
→ 这些场景暴露定义必须解决的歧义
```

### 与代码和数据手册交叉引用

```
用户说"DMA 完成后触发中断"
→ 查数据手册：此 MCU 的 DMA 是每次传输都触发中断，
  还是仅在半完成/全完成/错误时触发？
→ 查代码：ISR 是否真的处理了全部三种情况？
→ 如有矛盾：立即指出
```

### 即时更新 CONTEXT.md

术语解决后，**立即**写入 `CONTEXT.md` 作为词汇表条目——绝对不要批量处理。

格式：

```markdown
### <术语> — <一句话定义>

**上下文**：<此术语在本项目中何时以及为何重要>
**精确定义**：<2-3 句话，不含实现细节>
**区分于**：<此术语*不是*什么的关联术语>
**厂商说明**：<如果是厂商特定的，标注厂商>
**数据手册引用**：<章节/页码（如适用）>
```

### 谨慎提供 ADR

仅当以下三项全部满足时才创建 ADR：

1. **难以逆转**——以后改变主意的成本是有意义的
2. **缺少上下文会令人困惑**——未来的读者会问"为什么他们这样做？"
3. **真实权衡的结果**——存在真正的替代方案，你因特定原因选择了一个

嵌入式 ADR 触发条件：

```
✅ 写 ADR：
├── "为什么此传感器用 I2C 而不是 SPI？"（PCB 面积 vs 速度的权衡）
├── "为什么将 ISR 工作推迟到任务中而不是在 ISR 中处理？"（记录实时约束）
├── "为什么 DMA 缓冲区放在 SRAM1 而不是 SRAM2？"（与 flash 控制器的总线竞争）
└── "为什么不升级到新的 BLE controller？"（HCI 时序变了，硬件跟不上）

❌ 不写 ADR：
├── "为什么用 UART0 而不是 UART1？"（pinmux 可以解释——写注释即可）
├── "为什么波特率是 115200？"（行业惯例——写配置说明）
└── "为什么用 FreeRTOS？"（项目级决策已在 PROJECT-KNOWLEDGE-GRAPH.md 中记录）
```

ADR 格式：

```markdown
# ADR-<编号>：<标题>

**日期**：YYYY-MM-DD
**状态**：proposed | accepted | superseded

## 背景
当时的情况是什么？存在哪些约束？

## 决策
我们选择了什么？要具体——"用 SPI 8MHz with DMA"而不是"用 SPI"。

## 考虑的替代方案
- 方案 A：是什么以及为什么被拒绝
- 方案 B：是什么以及为什么被拒绝

## 后果
什么变得更容易？什么变得更困难？必须警惕什么？
```

## 与知识图谱协作

来自 `scan-embedded-project` 的 `PROJECT-KNOWLEDGE-GRAPH.md` 是领域模型的原材料。用它来：

- 种子初始词汇表：提取外设名称、协议术语、模块名称
- 交叉检查：用户的术语与图谱匹配吗？如果图谱称之为"USART1"而用户说"那个调试串口"，确定下来
- 检测矛盾：如果图谱显示 FreeRTOS 但用户描述了一个裸机 ISR 模式，问哪个是正确的
