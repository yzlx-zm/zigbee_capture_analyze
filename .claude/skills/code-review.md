# 代码审查（嵌入式）

对嵌入式代码进行双轴审查——**规范轴**（编码约定 + 嵌入式坏味基线 + MISRA）和**需求轴**（代码是否匹配驱动规范/数据手册/需求）。

两个轴作为**并行子代理**运行，然后此技能汇总结果。

## 流程

### 1. 确定基准点

捕获：`git diff <基准点>...HEAD`（三点 = 相对于 merge-base）。
同时：`git log <基准点>..HEAD --oneline`。

确认引用可解析且 diff 非空后继续。

### 2. 确定需求来源

按顺序搜索：
1. 提交消息中的 issue 引用（`#123`、`Closes #45`）
2. 用户作为参数传递的路径
3. `docs/`、`specs/` 或 `.scratch/` 下的驱动规范或 PRD
4. 代码注释中引用的数据手册章节
5. 以上都没有 → 需求轴跳过，报告"无可用规范"

### 3. 确定编码规范来源

按优先级排列（较高覆盖较低）：

1. 仓库中的 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`
2. 已记录的 MISRA-C 采用情况（哪些规则、哪些有偏离说明）
3. 厂商 SDK 的编码约定
4. 以上都没有 → 仅使用以下**嵌入式坏味基线**

### 嵌入式坏味基线

即使没有记录的规范，这些也适用。每条是**启发式方法，不是硬性违规**——始终是判断。已记录的工程规范覆盖基线。跳过工具已强制执行的任何内容。

#### 正确性（可能导致不可恢复的硬件故障）

**1. Volatile 缺失或误用**
- ISR 修改的全局变量未声明 `volatile` → 编译器可能优化掉读操作
- 不需要 `volatile` 的变量加了 `volatile` → 性能损失、掩盖真正的同步问题
- 检查：ISR ↔ 主循环共享变量、MMIO 指针、硬件状态寄存器

**2. 临界区错误**
- 关中断时间过长 → 错过截止时间
- 嵌套临界区 → 获取锁时可能死锁
- 遗漏临界区 → ISR 和任务间数据竞争
- 检查：所有共享数据访问路径、锁层级遵守情况

**3. ISR 内违规操作**
- ISR 中调用阻塞函数（`printf`、`malloc`、等信号量、等互斥锁）
- ISR 执行时间无界（循环依赖外部输入）
- ISR 中非原子外设寄存器访问
- 检查：ISR 调用树、最长执行路径

**4. 内存排序与屏障**
- DMA 描述符修改后未 clean cache / 加内存屏障
- 寄存器写入顺序未强制（ARM 上 `__DMB()`/`__DSB()`，RISC-V 上 `fence`）
- 强/弱序内存模型混用（Cortex-M vs Cortex-A）
- 检查：DMA 完成后缓存维护、`dma_wmb()` 使用

**5. 未定义行为**
- 有符号整数溢出（= UB，不是 wrap around）
- 移位超过位宽（32 位平台上 `x << 33`）
- 空指针解引用无 MPU 保护（Cortex-M0）
- 栈溢出无检测（静默破坏 .data 段）
- 检查：编译器警告、静态分析器、MISRA C 规则 12/13/18

#### 健壮性（可能导致部署设备变砖）

**6. 看门狗误用**
- 只在主循环中喂狗 → 子循环挂死检测不到
- 喂狗太快 → 卡死的任务永远不会触发复位
- 启动阶段无看门狗 → 初始化挂死 = 设备变砖
- 检查：喂狗位置独立性、窗口看门狗配置、启动超时保护

**7. 超时缺失**
- 轮询硬件状态寄存器无超时：`while (!(REG & FLAG));`
- I2C/SPI/UART 传输无超时 + 无重试
- 外部设备就绪等待无超时（传感器、射频芯片）
- 检查：每个读硬件的 `while` 循环除成功外都有退出条件

**8. 错误处理缺失**
- 外设初始化失败被静默忽略 → 后续操作在死硬件上进行
- `malloc` 返回值未检查（嵌入式堆很小，失败概率高）
- 协议栈回调错误码被忽略
- 检查：返回值覆盖范围、assert 位置、错误恢复路径

**9. 资源泄漏（嵌入式上更致命）**
- 未释放的信号量/互斥锁（有限池 → 一次泄漏 = 最终死锁）
- 定时器未停止/删除（RTOS 定时器池很小）
- 动态内存泄漏（嵌入式堆通常只有几 KB，几次就耗尽）
- 检查：init ↔ deinit 配对、open ↔ close、alloc ↔ free

#### 可维护性（给下一个工程师的成本）

**10. 魔法数字无注释**
- 裸寄存器地址：`0x40021000` → 使用 `#define` 或 CMSIS
- 裸时序值：`1000` → `#define I2C_TIMEOUT_MS 1000`
- 裸位掩码：`0x07` → `#define UART_PARITY_MASK 0x07`
- 例外：数据手册寄存器位域偏移可用移位宏，不一定是魔法数字

**11. 硬件耦合泄漏**
- 应用层代码直接操作外设寄存器 → HAL 被绕过
- 驱动实现细节泄漏到上层接口（返回寄存器值而非错误码）
- ISR 中包含业务逻辑而非通知任务
- 检查：抽象层穿透情况、依赖方向 vs 分层架构

**12. 平台相关代码未隔离**
- `#ifdef CONFIG_PLATFORM_X` 散落各处 → 收集到 `hal/` 或 `platform/`
- 同一函数的 FreeRTOS 和 bare-metal 变体混杂
- 检查：条件编译密度、HAL 接口清晰度

### 4. 并行启动两个子代理

**规范子代理 prompt**——包含：
- diff 命令和提交列表
- 步骤 3 中找到的规范源文件
- **嵌入式坏味基线**全文粘贴（子代理没有其他访问方式）
- 任务："按文件/hunk 报告：(a) diff 违反已记录规范的每个地方——引用规范文件 + 规则；(b) 发现的任何基线坏味：命名并引用 hunk。已记录规范的违规可以是硬性的；基线坏味始终是判断。跳过工具已强制执行的。"

**需求子代理 prompt**——包含：
- diff 和提交列表
- 规范路径或内容
- 任务："报告：(a) 规范要求但 diff 中缺失或不完整的内容；(b) diff 中规范未要求的行为（范围蔓延）；(c) 看起来实现了但实现有误的需求。每个发现引用规范行。"

### 5. 汇总

在 `## 规范轴` 和 `## 需求轴` 标题下呈现两份报告。**不要**跨轴合并或重排。

结尾：每轴发现总数，每轴内最严重问题。

## 为什么是双轴

- 遵循全部规范但实现了错误功能的代码 → **规范轴通过，需求轴失败**
- 完全匹配需求但违反嵌入式安全规则的代码 → **需求轴通过，规范轴失败**

分开报告阻止一个轴掩盖另一个轴。
