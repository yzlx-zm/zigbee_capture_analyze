# 场景 L1-2：Association 失败（已发现网络但加入失败）

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L1 网络形成与入网 | 状态：draft v1.1（二次审慎分析修订）
> 官方依据：docs.silabs.com "Network Activities"、UG235.02 "Common 802.15.4 MAC Processes"（8 步 Association 流程）、Zephyr ieee802154_frame.h（命令 ID/状态码权威定义）
> 官方错误码：EMBER_JOIN_FAILED (0x9B)、Association status 0x00/0x01/0x02
> 真实素材：`中继入网抓包(1).cubx`（scapy 解析，见第 12 层）
> **修订记录**：v1.0 → v1.1 修正第 2/3/4/5/12 层 — v1.0 示例 A 存在**时间关联错误**（把 27 秒后另一设备的拒绝响应关联给本请求）和**PAN 归属错误**（把同 PAN 多 router 响应误称"另一 PAN"）。二次审查用全局 req→resp 匹配（dst=req.src + 时间窗口）后重写。

---

## 0. 抓包可行性（数据现实层）

| 条件 | 要求 | 说明 |
|------|------|------|
| **最小抓包时长** | 覆盖入网操作全程（网络 steering 周期） | 从 Beacon Request 到 AssocResp，正常 1-2s 内完成；失败重试则更长 |
| **sniffer 位置** | 网络侧即可（实测可行） | Association 是设备↔协调器（或 router）点对点，sniffer 在任一节点附近均可听到（中继入网抓包网络侧抓到了完整流程） |
| **捕获信道** | 与网络信道一致 | 信道不对则整个流程不可见 |
| **覆盖盲区声明** | 成功分配的 AssocResp 可能被部分 PAN 听到而 sniffer 漏听 | 多 PAN 并存时，AssocResp 有多个（不同 PAN 各自响应），漏听一个不致命 |

**结论**：L1-2 的抓包条件比 L1-1 宽松 — 网络侧 sniffer 即可可靠判定。核心是抓到 **AssocReq 及其后 1-2s 内的 AssocResp**。

## 1. 场景识别（入口）

**用户描述关键词**：`入网失败`、`加入不了`、`连不上网`、`Association 失败`、`EMBER_JOIN_FAILED`、`0x9B`、`被拒绝`

**典型症状**：
- 设备能发现网络（Beacon 正常）但加入失败
- 设备侧日志：`EMBER_JOIN_FAILED` / `NWK Steering joining 0xAF87` 后失败 / `Network Steering Completed: FAILED`
- 反复重试仍失败

**与相邻场景的区分**（详见第 7 层）：
- 无 Beacon → **L1-1**（发现失败）
- Assoc 成功但拿不到 Network Key → **L1-3**（密钥分发失败）
- Assoc 成功 + Device Announce 后被踢 → **L1-4**（TC 拒绝）

---

## 2. 正常抓包基线

**健康流程**（IEEE 802.15.4 标准 Association，UG235.02 官方 8 步表）：

```
Step 1: E → C  Beacon Request（广播）         ← L1-1 的产物
Step 2: C → E  Beacon（含 Superframe spec，PermitJoin 标志）
Step 3: E → C  Association Request（源=长地址, 目标=短地址, 含 Capability Info）
Step 4: C → E  MAC Ack（确认收到 AssocReq）
Step 5: E → C  Data Request（源=长地址, 目标=短地址, intra-PAN）— 设备来取响应
Step 6: C → E  MAC Ack（Frame Pending 位=1，表示有数据待取）
Step 7: C → E  Association Response（短地址 + Association status）— 关键帧!
Step 8: E → C  MAC Ack
```

**健康判定**：Step 7 的 AssocResp **status=0x00（成功）** 且 short_addr ≠ 0xFFFF/0xFFFE。

**实测基线**（中继入网抓包，见第 12 层）：
- AssocReq 发出 → AssocResp 返回延迟：**~205ms**（成功案例 id=3217 → 3245；id=4935 → 4973 约 500ms）
- 成功响应：`addr=0xF67F status=0x00`（id=3245）、`addr=0x838D status=0x00`（id=4973）
- **同一 PAN 多 router 响应**：一个 AssocReq 可收到多个 AssocResp（来自不同 router），status 可能不一致 — 判定时必须按 dst 匹配到目标设备的请求

**Association status 含义**（Zephyr 权威定义）：

| status | 含义 |
|--------|------|
| 0x00 | **成功** |
| 0x01 | **PAN at capacity**（PAN 已满，无容量） |
| 0x02 | **PAN access denied**（PAN 拒绝接入） |
| 0x80+ | MAC primitive 保留范围 |

## 3. 异常表现

| 观察点 | 正常 | 异常（本场景） |
|--------|------|----------------|
| AssocReq 发出 | 有 | 有（Beacon 正常） |
| AssocResp 返回 | 有，status=0x00 | **无响应** 或 **status=0x01/0x02** |
| 短地址 | 分配 (≠0xFFFF) | 0xFFFF（拒绝时）或 0xFFFE（未分配） |
| 设备侧 | EMBER_NETWORK_UP | `EMBER_JOIN_FAILED (0x9B)` |

**两种异常子型**（根因不同，见第 6 层）：
- **A. 无响应型**：AssocReq 后窗口内无任何 AssocResp，且全局匹配确认该源无响应（协调器未处理/帧丢失）
- **B. 明确拒绝型**：AssocResp status=0x01（容量满）或 0x02（拒绝接入）且 **dst 匹配到目标设备的请求**（v1.1 强制：不能把其他设备的响应算进来）

---

## 4. 判定条件（可编程规则）

```
规则 L1-2-A（无响应型，高置信）:
  assoc_req_count > 0
  AND 在 assoc_req 后 2s 窗口内 assoc_resp_count == 0
  → L1-2 子型 A（无响应）

规则 L1-2-B（明确拒绝型，高置信）:
  assoc_resp.status in (0x01, 0x02)
  AND assoc_resp 对应已发出的 assoc_req
  → L1-2 子型 B（拒绝）
  - status=0x01 → 根因: PAN 容量满
  - status=0x02 → 根因: 协调器拒绝 (permit join=0 / 策略拒绝)

规则 L1-2-C（成功排除，中置信）:
  assoc_resp.status == 0x00 AND short_addr != 0xFFFF/0xFFFE
  → 排除 L1-2, 转 L1-3 (密钥分发)
```

**关键字段**：
- AssocReq：MAC 命令帧 cmd_id=**0x01**（scapy `Dot15d4Cmd.cmd_id`），源=长地址，payload=Capability Info (1 字节)
- AssocResp：MAC 命令帧 cmd_id=**0x02**，payload = short_addr (2 LE) + status (1)
- **req→resp 匹配：resp.dest_addr == req.src_addr**（v1.1 强制 — 不做全局匹配会误关联其他设备的响应，见修订记录）
- 拒绝特征：short_addr=0xFFFF（注意：**成功时为 0xFFFE 未分配 ≠ 拒绝的 0xFFFF**，易混淆，见第 7 层）

## 5. 直接证据（铁证）

| 优先级 | 证据 | 说明 |
|--------|------|------|
| ★★★ | AssocResp status=0x02（PAN access denied） | 协议级明确拒绝 — 铁证 |
| ★★★ | AssocResp status=0x01（PAN at capacity） | 容量问题 — 铁证 |
| ★★★ | AssocReq 后 2s 无 AssocResp + 设备侧 `EMBER_JOIN_FAILED (0x9B)` | 无响应型 — 设备日志佐证 |
| ★★ | AssocResp short_addr=0xFFFF | 未分配地址 = 拒绝/失败 |
| ★★ | 同一 PAN 多 router 响应混杂（部分成功部分拒绝，实测案例） | 必须按 dst 匹配目标设备、以分配给它的响应为准；"有拒绝响应"≠失败 |

**证据定位**：AssocReq 时刻 ±2s 窗口。

## 6. 根因链路

```
表象: 已发现网络但 Association 失败 (EMBER_JOIN_FAILED)
  ├─ 子型 A: 无 AssocResp（协调器无响应）
  │    ├─ 直接: AssocReq 未到达协调器 / 协调器未处理
  │    └─ 深层: 射频链路质量差 (关联 L3-9 非对称) / 协调器忙 / 干扰 (L7-2)
  └─ 子型 B: AssocResp status≠0x00（明确拒绝）
       ├─ status=0x01 (PAN at capacity):
       │    └─ 深层: 协调器/路由器的子设备表满 — 需要更多 router 分担或提高容量
       ├─ status=0x02 (PAN access denied):
       │    ├─ 深层 1: Permit Join 已关闭 (beacon 中 permit=0 但设备仍尝试 — 配置不一致)
       │    ├─ 深层 2: 协调器安全策略拒绝 (关联 L1-4 TC 拒绝, 但那是认证阶段)
       │    └─ 深层 3: 设备被协调器拉黑 (Remove Device 过的地址)
       └─ 混合: 多 PAN 场景选错网络
            └─ 深层: 设备扫描到的多个 PAN, 选中的 PAN 拒绝, 其余 PAN 接受但设备没换 (关联 L1-7)
```

## 7. 混淆项（长得像但不是）

| 混淆场景 | 抓包差异 | 排除方法 |
|----------|----------|----------|
| **L1-1 发现失败** | 无 Beacon / 无 AssocReq | 本场景必有 Beacon + AssocReq |
| **L1-3 密钥分发失败** | AssocResp status=0x00 但无 Transport Key | 看 AssocResp 成功与否 — 成功则不是 L1-2 |
| **L1-4 TC 拒绝** | Assoc 成功 + Device Announce → Leave (Rejoin=0) | TC 拒绝发生在**认证阶段**，Assoc 本身成功 |
| **0xFFFE ≠ 0xFFFF** | 成功但未分配地址（0xFFFE）vs 拒绝（0xFFFF） | 必须区分：0xFFFE 是"设备没要地址"，0xFFFF 是"拒绝" |
| **Multi-PAN 响应混杂** | 多个 AssocResp 来自不同 PAN（一个成功一个拒绝） | 看设备实际选择的 PAN 对应的响应 |

## 8. 自动检测盲区

| 盲区类型 | 本场景表现 | 后果 |
|----------|-----------|------|
| **设备未听到** | sniffer 听到 AssocResp status=0x00，但设备实际没收到（干扰/距离） | 设备侧实际失败，抓包看起来"成功" → 需设备日志交叉验证 |
| **sniffer 听不到** | AssocReq 被 sniffer 漏听（帧丢失），只见孤立 AssocResp | 无法关联 req→resp → 只能中置信 |
| **抓包未覆盖** | 设备加入的信道不在 sniffer 监听范围 | 流程完全不可见 |
| **时间窗口不足** | 只抓了 AssocReq 前或后的一侧 | 看不到完整 req→resp 配对 |

**铁律**：无响应型（子型 A）的"无 AssocResp"结论需谨慎 — 若 sniffer 覆盖质量差，可能漏听。高置信判定必须：AssocReq 被完整捕获 + 其后窗口干净（无对应 AssocResp）+ 设备侧 JOIN_FAILED 日志。

## 9. 置信度分级

| 置信度 | 判定条件 | 复核建议 |
|--------|----------|----------|
| **高** | AssocResp status=0x01/0x02 明确拒绝 或 AssocReq 完整 + 无响应 + 设备日志 JOIN_FAILED | 直接定位根因（容量/策略/链路） |
| **中** | 只有孤立 AssocResp（req 漏听）或仅设备日志无抓包 | 补抓包或查协调器侧日志 |
| **低** | 从网络整体帧统计推断（如拒绝响应多但无法关联具体设备） | 需要定向抓包 |
| **不可判定** | 抓包无任何 Assoc 相关帧 | 输出补抓指引 |

## 10. 人工复核清单

- [ ] 确认 Beacon 的 **PermitJoin 标志**：permit=0 但设备尝试加入 → 配置不一致（协调器开了但 beacon 没带，或设备无视）
- [ ] 确认 AssocResp 的 **status 值**：0x01 容量 / 0x02 拒绝 / 其他
- [ ] 确认 **short_addr**：0xFFFF（拒绝）vs 0xFFFE（未请求地址）vs 正常分配值
- [ ] 多 PAN 场景：设备选中的 PAN 是哪个，它的响应是什么
- [ ] 协调器侧日志：是否收到 AssocReq（MLME-ASSOCIATE.indication）
- [ ] 设备侧日志：`EMBER_JOIN_FAILED` 出现时机与重试节奏

## 11. 上下游关联

| 关联 | 场景 | 关系 |
|------|------|------|
| 上游 | **L1-1 发现失败** | Beacon 正常是进入本场景的前提 |
| 下游 | **L1-3 密钥分发失败** | Assoc 成功后拿不到 NWK Key（status=0x00 场景的下一步） |
| 下游 | **L1-4 TC 拒绝** | Assoc 成功后认证阶段被踢 |
| 同层 | **L1-7 误入错误 PAN** | 多 PAN 选错 → 混入本场景的"拒绝"表象 |
| 修复指向 | — | 容量满→扩容；permit join→打开并确认 beacon 传播；链路差→查 L3-9/L7-2 |

## 12. 判定示例（真实抓包）

**来源**：`D:\work\zigbee_capture\中继入网抓包(1).cubx`（网络侧，scapy 解析）

> **⚠️ 分析方法（v1.1 强制）**：req→resp 匹配必须用 **dst=req.src + 时间窗口**（全局匹配），不能只看目标帧附近窗口 — v1.0 因未做全局匹配而错误关联（详见修订记录）。

### 完整关联清单（全局匹配结果）

| AssocReq | 时间 | 源地址 | 匹配的 AssocResp | 结论 |
|---|---|---|---|---|
| id=1840 | ...595.985 | src=6238892841914422932 | **无**（后 5s 内 0 个 AssocResp） | 无响应型 |
| id=3217 | ...630.034 | src=11871832335072429739 | id=3245(成功 0xF67F) + id=3247/3251(拒 0xFFFF/0x02) | 成功（混合响应） |
| id=4935 | ...676.007 | src=11871831993377572712 | id=4973(成功 0x838D) | 成功 |
| **（孤儿）** | — | **设备 X** dst=11871831883910021981 | id=3047-3050(×4 拒, t=...623) + id=3433(成功 0x8A41) + id=3435-3438(×4 拒, t=...632) | **请求不在抓包内**（漏抓/更早） |

### 示例 A：无响应型（高置信 L1-2 子型 A）

**抓包片段**（id=1840，t=1780364595.985）：

```
t=+0.000s id=1840 AssocReq [cap=0xFB, pan=0xFFFF(广播), dst=广播, src=6238892841914422932]
t=+5.000s 内 0 个 AssocResp (cmd_id=0x02)
```

**特征**：AssocReq 发出后 **5s 窗口内无任何 AssocResp**，且全局匹配确认该源地址没有收到任何响应。

**判定**：**高置信 L1-2 子型 A**（无响应）。可能根因：请求未到达协调器 / 协调器未处理 / 链路问题。

**注意**：该请求 pan=0xFFFF（广播 PAN）较反常 — 正常 AssocReq 应指定目标 PAN（如 id=3217 的 pan=0x580C）。此细节存疑，需设备侧日志佐证，不擅自下结论。

### 示例 B：成功 + 拒绝混合（同 PAN 多 router）— 用于校准"健康"长什么样

**抓包片段**（id=3217，t=1780364630.034）：

```
t=-0.414s id=3146 BeaconReq
t=+0.000s id=3217 AssocReq [cap=0x8E, pan=0x580C]
t=+0.205s id=3245 AssocResp [addr=0xF67F status=0x00]  ← 成功! 分配地址
t=+0.208s id=3247 AssocResp [addr=0xFFFF status=0x02]  ← 另一 router 拒绝
t=+0.216s id=3251 AssocResp [addr=0xFFFF status=0x02]
```

**特征**：同一 AssocReq 收到 3 个 AssocResp — **1 个成功（0xF67F/0x00）+ 2 个拒绝（0xFFFF/0x02）**。三个响应 **dest_panid 均为 0x580C（同一 PAN）**，src 是三个不同 router（长地址各不相同）。

**判定**：**排除 L1-2**（对目标设备而言 Assoc 成功）。校准价值：健康 AssocResp 延迟 ~205ms；**同一 PAN 内多 router 响应且 status 不一致是正常现象** — 只看"有拒绝响应"就判失败是误判，必须按 dst 匹配到目标设备的请求、以分配给该设备的响应为准。

### 示例 C：孤儿响应组（分析盲区示例）— 不可判定

**抓包片段**（设备 X，t=1780364623 与 1780364632）：

```
t=...623.398 id=3047-3050 AssocResp [addr=0xFFFF status=0x02] ×4  dst=设备X
t=...632.461 id=3433 AssocResp [addr=0x8A41 status=0x00]         dst=设备X  ← 成功
t=...632.464 id=3435-3438 AssocResp [addr=0xFFFF status=0x02] ×4  dst=设备X
```

**特征**：设备 X 收到 5 个拒绝 + 1 个成功，但**它的 AssocReq 不在本抓包内**（无任何请求的 src=设备 X）。

**判定**：**不可判定**（对设备 X 而言）。有拒绝响应 ≠ 该设备失败 — 它最终收到了成功响应（0x8A41）。此组响应说明：抓包可能存在**漏抓请求**的情况 — 有 AssocResp 但无对应 AssocReq 时，不能默认"请求丢失 = 失败"，必须看响应内容。

### 示例 D：（待补）明确拒绝型（status=0x01/0x02 且匹配到请求）

**条件**：AssocResp status=0x01/0x02 且 dst 匹配到抓包内的 AssocReq（如示例 A 中若 1840 收到响应）。
