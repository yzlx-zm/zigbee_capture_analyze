# 场景 L1-3：密钥分发失败（Assoc 成功但拿不到/验证不了 NWK Key）

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L1 网络形成与入网 | 状态：**v1.1（官方依据 + 健康基线实测确认 + 判定规则修正；故障态待素材）**
> 官方依据：Silicon Labs SDK 源码 + 文档（链接见各层）：
> - APS 命令 ID：`zigbee_packet_types.h` `APS_COMMAND_TRANSPORT_KEY=5 / VERIFY_KEY=0x0F / VERIFY_KEY_CONFIRM=0x10`
> - 错误码：`sl_status.h` SL_STATUS_ZIGBEE_NO_NETWORK_KEY_RECEIVED (0x0C1B) / NO_LINK_KEY_RECEIVED (0x0C1C)
> - 设备侧 Leave：`network-steering(-v2).c`（Key verification failed → emberLeaveNetwork）
> - TC 侧踢人：`network-creator-security.c`（VERIFY_KEY_FAILURE/TIMEOUT → emberLeaveRequest rejoin=0）
> - 入网流程：docs.silabs.com「Zigbee 3.0 Security」/「Standard Security」
> ⚠️ **状态声明**：本场景的**正常基线**与**判定规则框架**已由官方依据 + 健康实测（`1-标准入网抓包-2.pcap`，tshark 权威解析）双重确认；**故障态的帧序列仍待复现素材验证**（标注 **[待素材]**）。

|------|------|------|

## 1. 场景识别（入口）

**用户描述关键词**：`密钥分发失败`、`拿不到密钥`、`NO_NETWORK_KEY_RECEIVED`、`0x0C1B`、`NO_LINK_KEY_RECEIVED`、`0x0C1C`、`Key verification failed`、`入网后离开`、`加入成功但无法通信`

**典型症状**：
- 设备 Association 成功（AssocResp status=0x00）但后续无法加密通信
- 设备侧日志：`EMBER_NO_NETWORK_KEY_RECEIVED (0x0C1B)` / `NO_LINK_KEY_RECEIVED (0x0C1C)` / `Key verification failed. Leaving network`
- 设备入网后短暂在线随即 Leave（网络侧可见 NWK Leave 帧）

**与相邻场景的区分**（详见第 7 层）：
- Assoc 本身失败 → **L1-2**
- Assoc 成功 + TC 主动拒绝（Remove Device）→ **L1-4 TC 拒绝**
- Assoc 成功 + 密钥流程完整 + 正常通信 → 排除本场景

## 2. 正常抓包基线 — ✅ 官方流程 + 健康实测确认

**健康流程**（集中式安全网络）：
```
① MAC Assoc (AssocReq→AssocResp status=0x00)
② (router→TC) Update Device (0x06)     [单跳直连 TC 时可能不可见]
③ TC→设备  Transport Key (0x05, key_type=0x01 NWK Key, 用预配置 Link Key 加密)
④ 设备 Device Announce (0x0013, 广播)   ← 需先有 NWK Key 才能发 (NWK 加密帧)
⑤ [Zigbee 3.0] TC→设备 Node Descriptor Req (0x0002)  ← 判定 Stack Compliance ≥ R21
⑥ 设备→TC  Request Key (0x08)          ← 请求新 TC Link Key
⑦ TC→设备  Transport Key (0x05, key_type=0x04 TC Link Key)
⑧ 设备→TC  Verify Key (0x0F)           ← 用新 Link Key 验证
⑨ TC→设备  Verify Key Confirm (0x10)   ← 密钥更新完成
⑩ 正常通信
```
> 官方来源：docs.silabs.com Zigbee 3.0 Security（③=Transport of network Key；⑤-⑨=Node Descriptor → Request Key → Transport Key(Link) → Verify Key Request → Verify Key Confirm）。

**实测观察（1-标准入网抓包-2, 0x2951 设备, tshark 权威解析）**：
```
t=20.088s 0x01 AssocReq    (第一次, 5.7s 无响应 — 单次 MISS, 与 L1-1 规则一致)
t=25.780s 0x01 AssocReq    (重试成功)
t=26.279s AssocResp [0x2951]            ← Assoc 成功
t=26.287s 0x05 Transport Key (TC→0x2951, key_type=0x01 NWK Key, seq=0)  ← Assoc 后 8ms
t=26.298s Link Status (0x2951→broadcast) ← 设备已能用 NWK Key 加密
t=26.302s Device Announce (0x0013) ×2 (26.630s)
t=27.527s 0x08 Request Key (0x2951→TC)
t=27.551s 0x05 Transport Key (TC→0x2951, key_type=0x04 TC Link Key)
t=27.563s 0x0F Verify Key (0x2951→TC, key_type=0x04)
t=27.599s 0x10 Verify Key Confirm (TC→0x2951)
```
- **AssocResp→TransportKey(NWK) 仅 8ms**；完整密钥流程 Assoc→Confirm 1.32s；TCLK 更新子流程（0x08→0x10）~72ms
- **Device Announce 在 TransportKey 之后 15ms** — 确认设备必须先拿到 NWK Key 才能广播（规则 A 修正依据）
- 全包 0 条 Leave / Rejoin / Network Status — 干净健康基线
- ⚠️ **修正记录**：骨架 v0.1 中的 "APScmd=0x20/0x38" 及 "TransportKey 未直接观测" 均为**错误观测**（疑为内部 scapy 解析偏差）。真实命令 ID 与 SDK 头文件枚举一致（0x05/0x08/0x0F/0x10）。

## 3. 异常表现 — [判定框架已确认，故障序列待素材]

| 观察点 | 正常 | 异常（本场景） |
|--------|------|----------------|
| AssocResp | status=0x00 | status=0x00（Assoc 成功！） |
| Transport Key (0x05, NWK) | ③ 出现 | **缺失**（TC 未分发）→ A1；或**出现但设备无反应**（解不出）→ A2 |
| Device Announce | ④ 出现（NWK 加密） | **缺失**（设备无 NWK Key 发不出）— 规则 A；出现 → 排除 A'（预配置 key） |
| Request Key (0x08) | ⑥ 出现 | 出现但无 0x05(TCLK) 响应 → 规则 B1 |
| Transport Key (0x05, TCLK) | ⑦ 出现 | 缺失（B1）或出现后流程中断（B2） |
| Verify Key (0x0F) | ⑧ 出现 | **缺失**（B2: 没收到/解不出 Link Key） |
| Verify Key Confirm (0x10) | ⑨ 出现 | 缺失 |
| 设备侧 | 正常通信 | `NO_NETWORK_KEY_RECEIVED`(0x0C1B, 规则A) / `NO_LINK_KEY_RECEIVED`(0x0C1C, 规则B1) / `Key verification failed`(规则B2) → **Leave** |
| TC 侧 | 无动作 | 规则B2: `Remove node 0xXXXX for failed key verification` → **Leave Request (rejoin=0)** |
| 后续 | 持续在线 | NWK Leave 帧后离线 / 尝试重入 |

## 4. 判定条件（可编程规则）— 规则框架已确认（v1.1 修正），故障阈值待素材

```
规则 L1-3-A（NWK Key 未分发型, 高置信）— 分两个形态:
  A1 (TC 未发): assoc_resp.status == 0x00
      AND transport_key_nwk (0x05, key_type=0x01) 缺失   ← 无线无此帧
      AND device_announce 缺失                          ← 设备无 NWK Key, 发不出加密 Announce
      AND (设备重试 Assoc / 最终 Leave)
      → 根因: TC 未分发 (TC 无设备 Link Key → EMBER_KEY_NOT_AUTHORIZED / 配置错误 / 帧丢失)
  A2 (发了解不出): transport_key_nwk (0x05) **出现**
      AND device_announce 缺失                          ← 设备解不出, 拿不到 NWK Key
      AND 无任何加密后续帧 (无 0x08 / 无数据)
      → 根因: 设备侧预配置 Link Key 与 TC 不一致 (install code 烧录错误)
  两形态共同官方对应: EMBER_NO_NETWORK_KEY_RECEIVED (0x0C1B)
    ("attempt to join a Secured Network, but the device did not receive a Network Key")
  【v1.1 修正】原 v1.0 写 "device_announce 出现" 是错的: Announce 是 NWK 加密帧,
  实测在 TransportKey 后 15ms (26.302s vs 26.287s) — TransportKey 缺失时设备无法发 Announce。
  A2 与 B2 的区分: A2 无 announce (NWK Key 都没拿到); B2 有 announce (已入网, 仅 TCLK 验证失败)。

规则 L1-3-A'（排除: preconfigured NWK Key 场景）:
  assoc_resp.status == 0x00
  AND transport_key_nwk 缺失
  AND device_announce 出现                          ← 有 NWK Key 才能发 Announce
  → 排除 L1-3 (设备 preconfigured NWK Key / secure rejoin, 无 TransportKey 属正常)

规则 L1-3-B1（TCLK 更新无响应型, 高置信, 官方路径确认）:
  request_key (0x08) 出现
  AND 5s 窗口内无 transport_key_tclk (0x05, key_type=0x04) 响应
  AND 设备 Leave
  → L1-3 命中 (根因: TC 策略 DENY / TC 不响应 key 请求)
    官方路径: update_tc_link_key_status_cb default
              (keyStatus=0x04 KEY_ESTABLISHMENT_TIMEOUT) → leave + 0x0C1C
              ("After a device joined, a Link Key was requested but no response")

规则 L1-3-B2（Verify 失败型, 高置信, 官方路径确认）:
  transport_key_tclk (0x05, key_type=0x04) 出现
  AND (verify_key (0x0F) 缺失 或 verify_key_confirm (0x10) 缺失)
  AND (设备 Leave 或 TC Leave Request (NWK 0x04, rejoin=0))
  → L1-3 命中 (根因: TC Link Key 不匹配 → 设备解不出/验证失败 → 离开)
    设备侧: finishSteering verify_tclk 失败 → "Key verification failed. Leaving network"
            → emberLeaveNetwork()
    TC 侧:  EmberKeyStatus 0x32 (VERIFY_KEY_TIMEOUT) / 0x33 (VERIFY_KEY_FAILURE)
            → emberLeaveRequest(dest, eui, 0)  [rejoin=0, 不告知可重入]

规则 L1-3-C（排除）:
  verify_key_confirm (0x10) 出现                    ← 密钥流程完整
  → 排除 L1-3 (密钥分发与验证成功)
```

**关键字段**（官方确认）：
- Transport Key：APS cmd 0x05；payload `key_type`(1B) + key + seqno + dest EUI64 + src EUI64；key_type: 0x01=Residential NWK Key, 0x03=App Link Key, 0x04=TC Link Key
- Request Key：APS cmd 0x08（设备向 TC 请求 Link Key）
- Verify Key：APS cmd 0x0F（设备→TC，验证新 Link Key）
- Verify Key Confirm：APS cmd 0x10（TC→设备，确认完成）
- Leave Request：NWK cmd 0x04（TC 踢人时 rejoin flag=0，即"不告知可重入"）

## 6. 根因链路 — [骨架, 官方部分确认]

```
表象: Assoc 成功但无法通信 / 入网后立即 Leave
  ├─ 直接原因 1: TC 未发送 Transport Key (NWK) — 无线无 0x05 帧
  │    ├─ 深层: TC 安全配置错误 / TC link key 表无该设备 → EMBER_KEY_NOT_AUTHORIZED
  │    └─ 表现: 规则 A1 (0x0C1B)
  │    (注: TC 明确拒绝属 L1-4 (Remove Device 0x07), 不是本场景)
  ├─ 直接原因 2: Transport Key 发出但设备解不出 (预配置 Link Key 不匹配)
  │    ├─ 深层: install code 不一致 / 设备侧 key 烧录错误 (关联 P5)
  │    └─ 表现: 规则 A2 (0x0C1B, 帧级 0x05 出现但设备无反应)
  ├─ 直接原因 3: 设备收到 NWK Key, 但 TCLK 更新失败
  │    ├─ Request Key (0x08) 无响应 (TC 策略 DENY) → 0x0C1C (NO_LINK_KEY_RECEIVED) → 规则 B1
  │    ├─ Verify Key (0x0F) 验证失败 → "Key verification failed" + TC 侧踢人 (0x33) → 规则 B2
  │    └─ 表现: 规则 B1 / B2
  ├─ 直接原因 4: Transport Key 帧丢失 (单播, 链路问题)
  │    ├─ 深层: 关联 L3-9 非对称 / L7-2 干扰
  │    └─ 表现: 规则 A1 (帧级 0x05 缺失)
  └─ 直接原因 5: 设备 preconfigured NWK Key 但配置错误
       └─ 深层: 预配置密钥与实际网络不符 → 验证失败 (0x0C1A 明文 key / 0x0C1D 需预配置)
```

## 7. 混淆项（长得像但不是）— [骨架]

| 混淆场景 | 抓包差异 | 排除方法 |
|----------|----------|----------|
| **L1-4 TC 拒绝** | Assoc 成功 + **Remove Device (APS 0x07)** 发给 parent（官方 standard-security: TC deny → Remove Device） | **帧级区分: 有无 0x07** — L1-4 有 0x07；L1-3-A 无 0x05 也**无 0x07**（TC 允许但没发 key） |
| **preconfigured NWK Key 场景** | Assoc 成功 + 无 0x05(NWK) + **Announce 出现** + 正常通信 | 规则 A' — Announce 有 NWK Key 才能发 |
| **A2 vs B2 混淆** | A2: 0x05(NWK) 出现 + **无 announce**（NWK Key 没拿到）+ 无后续；B2: announce 出现（已入网）+ 仅 TCLK 流程中断 | **以 announce 有无区分** — A2 设备还在入网重试，B2 设备已入网 |
| **L1-2 Association 失败** | AssocResp status≠0x00 | 本场景 Assoc 成功 |
| **设备主动离网** | 正常密钥流程完整 (0x05→0x08→0x05→0x0F→0x10) + 设备主动 Leave (request=1) | 看密钥流程是否完整 + Leave 方向/标志 |

## 8. 自动检测盲区 — [骨架]

| 盲区类型 | 本场景表现 | 后果 |
|----------|-----------|------|
| **sniffer 听不到 key 内容** | Transport Key 命令 ID/key_type 可见，但 key 字段不可解（缺 TC Link Key） | 判定流程不受影响（只需命令 ID）；无法对比密钥值 |
| **设备未听到** | sniffer 抓到 Transport Key，但设备实际没收到（单播丢失） | "有分发"≠"设备收到" — 需设备日志或 Verify Key 缺失佐证 |
| **Update Device 不可见** | 单跳直连 TC 时 0x06 帧不出现 | 不影响判定（判定基于 0x05/0x08/0x0F/0x10） |
| **抓包未覆盖** | 密钥分发在入网后立即发生（实测 0.5s 内），抓包开始晚了就错过 | 必须从 Assoc 成功前开始抓 |
| **内部解析偏差 ⚠️** | 骨架 v0.1 的 0x20/0x38 即内部 scapy 解析偏差产物（真实 0x08/0x05/0x10） | 检测器读取 APS 命令 ID 必须用 tshark 权威解析或修正后的解析 **[待验证: cubx 路径 scapy 命令 ID 一致性]** |

## 9. 置信度分级 — [框架确认]

| 置信度 | 判定条件 | 复核建议 |
|--------|----------|----------|
| **高** | Assoc 成功 + 密钥帧缺失/中断 + 设备 Leave + 设备侧错误码日志 (0x0C1B/0x0C1C/Key verification failed) 或 TC 侧 Leave rejoin=0 | 直接定位根因（TC 配置/密钥） |
| **中** | 帧级证据完整（Assoc 成功 + 密钥帧缺失/中断 + Leave）但无设备日志 | 查设备日志确认错误码 |
| **低** | 仅看到 Leave 无密钥流程上下文 | 补抓包（从 Assoc 前开始） |
| **不可判定** | 抓包未覆盖 Assoc 或密钥窗口 | 需重抓 |

## 10. 人工复核清单 — [框架确认]

- [ ] AssocResp status 是否 0x00（确认不是 L1-2）
- [ ] Transport Key (0x05, key_type=0x01 NWK) 是否存在 — 区分"没发"（规则A）和"发了解不出"（EMBER_KEY_NOT_AUTHORIZED）
- [ ] Device Announce 是否出现 — 缺失佐证规则 A；出现则查是否 preconfigured key（规则 A'）
- [ ] Request Key (0x08) 有无 0x05(TCLK) 响应 — 无响应 → 规则 B1（TC 策略 DENY）
- [ ] Verify Key (0x0F) / Confirm (0x10) 是否完整 — 中断 → 规则 B2（密钥不匹配）
- [ ] 设备 Leave 帧方向：设备主动（request=1）vs TC 踢人（rejoin=0）
- [ ] sniffer 是否持有 TC Link Key（决定 key 内容可解性）
- [ ] 设备侧日志：`NO_NETWORK_KEY_RECEIVED` / `Key verification failed` / `NO_LINK_KEY_RECEIVED`
- [ ] 设备 preconfigured NWK Key / install code 配置是否正确
