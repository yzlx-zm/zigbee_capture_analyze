# 场景 L1-3：密钥分发失败（Assoc 成功但拿不到 NWK Key）

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L1 网络形成与入网 | 状态：**draft v0.1（骨架，待素材验证）**
> 官方依据：network-steering-v2.c `finishSteeringEventHandler`（TC Key 验证失败 → Leave）、Zigbee spec r22 §3.6.1（Transport Key）
> 官方错误码：EMBER_NO_NETWORK_KEY_RECEIVED (0x0C1B)
> ⚠️ **状态声明**：本场景尚**未完成素材验证**。健康基线素材（标准入网抓包-2）有 VerifyKey 但 TransportKey 未直接观测；故障素材待复现。以下内容为骨架 + 官方依据，标注 **[待验证]** 的层不可作为判定依据。

---

## 0. 抓包可行性（数据现实层）— [部分待验证]

| 条件 | 要求 | 说明 |
|------|------|------|
| **最小抓包时长** | Assoc 成功后 ~5s（密钥分发窗口） | Transport Key → Verify Key → (可选 Confirm Key) |
| **sniffer 位置** | 网络侧即可 | Transport Key 是 TC(协调器) → 设备 单播 |
| **捕获信道** | 与网络信道一致 | — |
| **覆盖盲区** | Transport Key 用 Link Key 加密，sniffer 必须持有 TC Link Key 才能解出 | 无 Link Key 时 Transport Key 帧存在但不可见（加密） |

**⚠️ 关键盲区**：标准入网抓包-2 中 VerifyKey 存在但 TransportKey(0x05) 未直接观测 — 两种可能：① 设备 preconfigured NWK Key（跳过 Transport Key）；② Transport Key 在未解密帧中（缺 Link Key）。**[待验证]**

---

## 1. 场景识别（入口）

**用户描述关键词**：`密钥分发失败`、`拿不到密钥`、`NO_NETWORK_KEY_RECEIVED`、`0x0C1B`、`入网后离开`、`加入成功但无法通信`

**典型症状**：
- 设备 Association 成功（AssocResp status=0x00）但后续无法加密通信
- 设备侧日志：`EMBER_NO_NETWORK_KEY_RECEIVED` / `Key verification failed`
- 设备入网后短暂在线随即 Leave（官方行为：TC Key 验证失败 → `emberLeaveNetwork()`）

**与相邻场景的区分**（详见第 7 层）：
- Assoc 本身失败 → **L1-2**
- Assoc 成功 + Device Announce → 立即 Leave (Rejoin=0) 但无 Transport Key → **本场景**（或 L1-4 TC 拒绝，看有无 Remove Device）
- Assoc 成功 + 正常通信 → 排除本场景

---

## 2. 正常抓包基线 — [部分待验证]

**健康流程**（集中式安全网络，Zigbee 入网标准）：
```
AssocResp status=0x00 (设备获得短地址)
  → Device Announce (0x0013, 广播)
  → Transport Key (APS cmd 0x05, TC→设备, 用 TC Link Key 加密)
     - key_type=1 (Network Key) 或 key_type=4 (TC Link Key)
     - 含加密的 NWK Key + key_seqnum + dest EUI64 + src EUI64
  → Verify Key (APS cmd 0x0F, 设备→TC, 用新 Link Key 加密)
  → (可选) Confirm Key (APS cmd 0x10)
  → 正常通信
```

**实测观察（标准入网抓包-2, 0x2951 设备）**：
```
t=26.279s AssocResp [0x2951/0x00]
t=26.302s Device Announce ×3
t=27.528s APScmd=0x20 (0x2951→0x0000)   ← [待确认] 命令含义
t=27.551s APScmd=0x38 (0x0000→0x2951)   ← [待确认] 命令含义
t=27.563s VerifyKey (0x2951→0x0000)      ← 密钥验证
t=27.599s APScmd=0x20 (0x0000→0x2951)
```

**⚠️ 待查点**：TransportKey(0x05) 未直接观测。0x20/0x38 非标准 APS 命令 ID — 可能是 scapy 解析偏差或厂商私有命令。**[待验证]**

## 3. 异常表现 — [待验证]

| 观察点 | 正常 | 异常（本场景） |
|--------|------|----------------|
| AssocResp | status=0x00 | status=0x00（Assoc 成功！） |
| Transport Key | TC→设备 单播 | **缺失** 或 发出但设备无法解密 |
| Verify Key | 设备→TC | **缺失**（设备没收到/解不出 NWK Key） |
| 设备侧 | 正常通信 | `NO_NETWORK_KEY_RECEIVED` → **Leave** |
| 后续 | 持续在线 | Leave (rejoin=1 尝试重入) 或完全离线 |

## 4. 判定条件（可编程规则）— [骨架，待素材验证]

```
规则 L1-3-A（Transport Key 缺失，高置信，待验证）:
  assoc_resp.status == 0x00                          ← Assoc 成功
  AND device_announce 出现                           ← 设备已入网
  AND transport_key (APS cmd 0x05) 在 5s 窗口内缺失   ← 无密钥分发
  AND verify_key 缺失
  → L1-3 命中 (根因: TC 未分发 / 分发帧丢失)

规则 L1-3-B（验证失败型，高置信，官方确认）:
  transport_key 出现
  AND verify_key 缺失 或 Confirm Key status != SUCCESS
  → L1-3 命中 (根因: TC Link Key 不匹配 → 解密失败 → 设备 Leave)

规则 L1-3-C（排除）:
  verify_key 出现 AND (后续正常通信或 rejoin 成功)
  → 排除 L1-3 (密钥验证成功)
```

**关键字段**：
- Transport Key：APS cmd 0x05，payload 含 key_type/key/dest EUI64/src EUI64
- Verify Key：APS cmd 0x0F
- Confirm Key：APS cmd 0x10，含 status

## 5. 直接证据（铁证）— [待验证]

| 优先级 | 证据 | 说明 |
|--------|------|------|
| ★★★ | 设备侧 `EMBER_NO_NETWORK_KEY_RECEIVED (0x0C1B)` 日志 | 协议栈确认：Assoc 成功但密钥没到 |
| ★★★ | Assoc 成功 + Transport Key 缺失 + 设备随后 Leave | 帧级确认（规则 A） |
| ★★★ | Transport Key 出现但 Verify Key 缺失 + 设备 Leave | 帧级确认（规则 B，官方行为：Key verification failed → emberLeaveNetwork） |
| ★★ | Device Announce 后无任何加密数据帧 | 设备无 NWK Key，无法参与加密通信 |

## 6. 根因链路 — [骨架]

```
表象: Assoc 成功但无法通信 / 入网后立即 Leave
  ├─ 直接原因 1: TC 未发送 Transport Key
  │    └─ 深层: TC 安全配置错误 / TC 侧无设备 EUI64 记录 (关联 L1-5 大网络多跳)
  ├─ 直接原因 2: Transport Key 发出但设备解不出 (TC Link Key 不匹配)
  │    └─ 深层: install code 不一致 / TC Link Key 更新未同步 (关联 P5)
  ├─ 直接原因 3: Transport Key 帧丢失 (单播, 链路问题)
  │    └─ 深层: 关联 L3-9 非对称 / L7-2 干扰
  └─ 直接原因 4: 设备 preconfigured NWK Key 但配置错误
       └─ 深层: 预配置密钥与实际网络不符 → 验证失败
```

## 7. 混淆项（长得像但不是）— [骨架]

| 混淆场景 | 抓包差异 | 排除方法 |
|----------|----------|----------|
| **L1-4 TC 拒绝** | Assoc 成功 + Device Announce → Leave，但可能伴随 Remove Device 或 Update Device 拒绝 | 看有无 Transport Key 分发尝试 — L1-3 有 Assoc 成功但密钥流程中断，L1-4 是 TC 主动拒绝 |
| **L1-2 Association 失败** | AssocResp status≠0x00 | 本场景 Assoc 成功 |
| **设备主动离网** | 正常密钥流程 + 设备主动 Leave (request=1) | 看密钥流程是否完整 |

## 8. 自动检测盲区 — [骨架]

| 盲区类型 | 本场景表现 | 后果 |
|----------|-----------|------|
| **sniffer 听不到** | Transport Key 加密且 sniffer 无 TC Link Key → 帧可见但 payload 不可解 | 无法确认 key_type/dest EUI64 — 只能看到"有 Transport Key 帧" |
| **设备未听到** | sniffer 抓到 Transport Key，但设备实际没收到（单播丢失） | "有分发"≠"设备收到" — 需设备日志或 Verify Key 缺失佐证 |
| **抓包未覆盖** | 密钥分发在入网后立即发生，抓包开始晚了就错过 | 必须从 Assoc 成功前开始抓 |

## 9. 置信度分级 — [骨架]

| 置信度 | 判定条件 | 复核建议 |
|--------|----------|----------|
| **高** | Assoc 成功 + Transport Key 缺失/Verify Key 缺失 + 设备 Leave + 设备侧 0x0C1B 日志 | 直接定位根因（TC 配置/密钥） |
| **中** | 帧级证据完整但无设备日志 | 查设备日志确认 NO_NETWORK_KEY_RECEIVED |
| **低** | 仅看到 Leave 无密钥流程上下文 | 补抓包（从 Assoc 前开始） |
| **不可判定** | sniffer 无 TC Link Key，Transport Key 全程不可解 | 需设备侧日志或带 Link Key 的抓包 |

## 10. 人工复核清单 — [骨架]

- [ ] AssocResp status 是否 0x00（确认不是 L1-2）
- [ ] Transport Key (cmd 0x05) 是否存在 — 区分"没发"和"发了解不出"
- [ ] Verify Key (cmd 0x0F) 是否存在 — 区分"设备没收到"和"验证失败"
- [ ] sniffer 是否持有 TC Link Key（决定 Transport Key 可解性）
- [ ] 设备侧日志：`NO_NETWORK_KEY_RECEIVED` / `Key verification failed` / `EMBER_ERR_FATAL`
- [ ] 设备 preconfigured NWK Key 配置是否正确
