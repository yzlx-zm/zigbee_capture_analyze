## 模式 1：DA13 网络 — 下行源路由失败 (0x0B)

**规律**（7 个故障包一致）：
- 0x0B **全由同一中继发出**（入网失败系列 = 0x703E；网关修改系列 = 0x87AB）
- 0x0B 起始距设备 Announce **2.4~5.0s**——设备刚入网后立即开始下行失败
- target = 刚入网的那台设备（每包一台）
- 时长两态：网关修改系列短促（3-6 轮/3-5s）；入网失败系列持续（8-12 轮/40-67s）
- **入网成功 ≠ 下行转发正常**：标注"网关修改-入网成功"的包依然带 0x0B

**与 838D 案例同构**：0x1885→0x838D（Confirm 经中继转发失败）——DA13 网络的 0x703E/0x87AB 对刚入网设备的下行失败是同一机制（L3-5-R1）。

**健康对照**（DA13-2 / 艺山网关修改 = 0 NS）→ 特定配置下完全干净，问题与中继配置/网关配置组合相关。

## 模式 2：G32 网络 — 中继 0xBE5A 双向路由失败 (0x0C) + 间接超时 (0x06)

**G32_0626**（用户提供，运营期 36 分钟抓包，无入网活动）：

**帧方向全解**（Network Status 帧 = [src][dst][code][dest_addr]，方向信息丰富）：
- **0x0C ×216，src 全 = 0xBE5A**（中继/父节点）：
  - `0xBE5A → 0x0000, dest=0xBE5A` ×100（全程 1748s）：**发往 0xBE5A 自己的 MTORR 失败**（下行）
  - `0xBE5A → 0x0000, dest=0xEE48` ×86（1125s）：**发往 0xEE48 的 MTORR 失败**（下行）
  - `0xBE5A → 0xEE48, dest=0x0000` ×30（1125s）：**0xEE48 的上行失败**（0xBE5A 通知源设备）
- **0x06 ×38**（`0xBE5A → 0x0000`）：父节点 0xBE5A 报告**发往 0xEE48 的间接消息过期**（INDIRECT_TRANSACTION_EXPIRY）
- **0xEE48 = 重度轮询 SED**：MAC Data Request ×1933（全部发往 0xBE5A，间隔 0-12.4s）+ Route Record ×48（中继=[0xBE5A]）
- 0xBE5A = 活跃中继：Link Status ×109（**邻居仅 0x0000**）、Data ×235 全发 0x0000

**修正结论（2026-08-05 v2，用户指出原结论过于简化）**：
⚠️ v1 结论"0xBE5A 上行 MTORR 持续失败"不准确。帧方向显示：
1. **下行失败为主**（dest=0xBE5A/0xEE48 共 186 条）：协调器/其他设备发往 0xBE5A 和 0xEE48 的消息失败
2. **上行失败为辅**（dest=0x0000 ×30）：0xEE48 的上行数据经 0xBE5A 转发失败
3. **0x06 间接超时 ×38 与 poll ×1933 矛盾**：0xEE48 疯狂 poll 但 0xBE5A 的间接消息仍过期
   → poll 与间接传输机制断裂：0xBE5A 收到 poll 但无法回传缓存数据（下行链路/路由表异常），
   或 0xBE5A 的间接队列处理异常（消息在队列中过期）
4. **根因指向 0xBE5A↔0xEE48 链路的双向路由异常**（0xBE5A 邻居表只有 0x0000，看不到 0xEE48 直接邻居，
   但 0xEE48 poll 它 → 可能是非直连的父代理关系，或 MAC 层可达而 NWK 路由表失效）

**检测器启示**：0x0C 的 **dest 字段决定失败方向**（dest=0x0000 → 上行；dest=其他 → 发往该设备的下行失败），
L3-5-R2 检测器需按 dest 细分方向 [待增强]。

## 模式 4：G32 大包 08031620 (54403 包) — 无 NS 但 MTORR 高频 [观察]

**特征**（8 月 3 日, G32 专项分析目录）：
- Network Status = **0**（无错误码）; Leave/Rejoin = 0; L3-5 判 HEALTHY
- 路由器: 协调器 + 0x4DEE + 0xE091（共 3 台）; 协调器向 3 台设备大量下发 Data（各 ~260-276 次）
- **MTORR ×771 / 43 分钟 = 每 3.4s 一次**（⚠️ 健康默认 60s 周期!）

**对比 G32_0626**: MTORR 335 次/2389s = 每 7.2s 一次 — **两个 G32 包都高频**。

**解读（诚实, 两种可能）**：
1. 协调器 MTORR 周期配置过短（自研网关配置项）— 需用户确认配置
2. 路由错误持续触发 MTORR 重建（route error 不保证送达, sniffer 未捕获 — 官方盲区）→ 隐含路由问题

**检测器启示**: MTORR 频率（间隔统计）作为独立观察信号已加入 self_heal 输出;
高频 MTORR 不能直接判 L3-5（配置 vs 隐含问题需区分）, 标 [观察, 需配置信息佐证]。

## 根因方向（供现场/网关侧排查）

1. **DA13 下行模式**：中继对刚入网设备的下行源路由失败 — 查中继的源路由表更新时机、网关修改的配置项
   （"网关修改"系列 v1→v3 仍在报错 → 修改项未覆盖下行问题；艺山网关=健康 → 配置组合差异）
2. **G32 上行模式**：中继 0xBE5A 上行 MTORR 持续失败 + 间接超时 — 查该中继的上行链路/邻居表/
   子设备 poll 行为（0xEE48 的间接消息为何过期）
3. **健康对照启示**：同一网关（DA13）不同配置干净 vs 报错 → 配置可复现性，建议对比
   "艺山网关修改"与"网关修改 v1-v3"的差异点
