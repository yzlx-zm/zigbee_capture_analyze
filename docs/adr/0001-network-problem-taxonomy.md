# ADR-0001：Zigbee 网络问题分类框架（Taxonomy）作为分析引擎基准

**日期**：2026-08-01
**状态**：accepted

## 背景

工具的核心演进方向确定为：**导入问题包（抓包文件 + 问题描述）→ 自动定位分析 → 人工复核**。

现有诊断基础：
- `diagnosis_playbook.md` — 5 大类 19 场景实战手册（现象→证据链→诊断步骤→根因→解决）
- `network_analysis_kb.md` — 17 种帧类型详解

但 19 场景是**按实战经验手写**的，未对照协议规范系统性覆盖。存在结构性缺口：睡眠设备（SED）专项、MAC 层错误码、设备硬件故障、源路由/MTORR 失效、间接队列问题等均无场景。

## 决策

采用 **8 大类 ~55 场景** 的问题分类框架（`docs/network_problems_taxonomy.md`）作为分析引擎的分类基准：

```
L1 网络形成与入网 (7)   L2 设备在线维持 (6)    L3 运营期核心 (20)
L4 网络级维护 (5)       L5 应用/功能层 (4)    L6 睡眠设备 SED (5)
L7 MAC/物理层 (4)       L8 设备硬件/固件 (3)
```

关键约束（框架的设计承诺）：

1. **每个场景必须有帧级证据链** — Network Status 错误码（0x00-0x13 完整 20 码）、MAC 状态码（0x14/0x15/0x41/0xA1）、ZCL 状态码（0xC0-C2）、帧序列模式。这保证场景可被分析脚本自动检测，不依赖人工经验。
2. **与现有 playbook 兼容** — 原 P1-P5 是框架的已覆盖子集，playbook 保留为"人工复核手册"，taxonomy 是超集。
3. **错误码速查表是黄金标准** — 每个错误码映射到场景 ID，分析引擎的规则层以错误码为第一信号源。

## 考虑的替代方案

- **方案 A：仅扩展现有 playbook（P6、P7...）**
  被拒绝。playbook 是"人工诊断手册"的定位，按现象组织；分析引擎需要的是"自动可检测"的信号组织。混合会让两个用途都变差。
- **方案 B：直接用 AI 语义判断（问题描述 → 大模型推理定位）**
  被拒绝。当前阶段无 AI 能力配置（AI 助手是 M5 里程碑），且人工复核要求可解释的证据链；规则化检测是必要的地基，AI 只能作为上层加速。
- **方案 C：按协议层组织（MAC/NWK/APS/ZCL）**
  被拒绝。工程师描述问题时按"现象/生命周期"组织（"设备掉线了"、"入网失败"），不按协议层思考。分类必须与用户心智模型对齐。

## 后果

**变得更容易**：
- "问题描述 → 场景映射"可规则化（症状关键词 → 场景 ID → 检测脚本）
- 自动检测可按场景 ID 对号入座，检测结果直接关联 playbook 诊断步骤供人工复核
- 新场景扩展有明确锚点（新错误码 → 新场景 ID）

**变得更困难**：
- 55 场景的检测规则实现是持续工作（每个场景需要明确帧特征阈值）
- 分类框架固化后，改框架（如合并/重命名场景）成本高 — 后续只允许增量（新场景追加），不允许结构性调整

**必须警惕**：
- 场景 ID 一旦被检测脚本/文档引用，不可重编号 — 新场景用新 ID（如 L6-S6）
- 错误码映射表需随 Zigbee 规范更新（R23+ DLK 等新特性）增量补充
