# 场景 L1-1：信道/网络发现失败（无 Beacon）

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L1 网络形成与入网 | 状态：draft v1.1（二次审慎分析修订）
> 官方依据：network-steering.c（Simplicity SDK）、form-and-join.c（Gecko SDK）、docs.silabs.com "Network Activities"
> 官方错误码：EMBER_NO_BEACONS (0xAB)、SL_STATUS_NO_BEACONS
> **修订记录**：v1.0 → v1.1 修正第 8/12 层 — 原"中继入网抓包无 Beacon Request"结论因帧识别错误被推翻（用 `raw[1]==0x07` 判断命令 ID，实为序列号）；改用 scapy `Dot15d4Cmd.cmd_id` 正确解析后：该抓包含 32 个 Beacon Request 且 **32/32 全部有响应**，是**健康基线的真实示例**而非盲区案例。

---

## 0. 抓包可行性（数据现实层）

| 条件 | 要求 | 说明 |
|------|------|------|
| **最小抓包时长** | ≥ 一个完整 Network Steering 周期 | 主信道掩码扫描（默认 BIT32(11)\|BIT32(14)）→ 次信道全扫 → 换密钥策略重试（install code → centralized → ZigbeeAlliance09 → distributed），完整流程可达数十秒 |
| **sniffer 位置** | **必须在加入设备附近** | Beacon Request 是**单跳广播**（MAC 层命令，跨 PAN 边界但不过路由）。sniffer 若只监听网络侧，**听不到 Beacon Request**，只能看到 beacon 广播流 |
| **捕获信道** | 覆盖设备的扫描信道掩码 | sniffer 单信道监听时，只能看到该信道上的 beacon |
| **覆盖盲区声明** | 若抓包**无任何 Beacon Request**（且设备侧无日志），无法区分"设备没发请求"和"请求没被听到" | 不可判定；但若有 request 记录（实测网络侧可听到，见示例 A），则本约束放宽 |

**结论**：实测表明**网络侧 sniffer 能听到 Beacon Request**（中继入网抓包 32 个 request 全部可见）— v1.0"网络侧听不到 request"的假设已被推翻。L1-1 判定真正依赖的是：**有 request 记录 + 无响应**（异常）vs **有 request + 有响应**（健康）。唯一盲区是 request 本身都抓不到的场景（设备距离远/信道未监听），此时不可判定。

## 1. 场景识别（入口）

**用户描述关键词**：`入网失败`、`找不到网络`、`搜不到网`、`设备无法加入`、`Beacon Request 无响应`、`NO_BEACONS`、`0xAB`

**典型症状**：
- 新设备按入网键后一直闪烁/等待，始终不加入
- 设备侧日志：`EMBER_NO_BEACONS` / `NWK Steering Completed: FAILED (0x94)`
- 网络侧：无任何入网活动迹象

**与其他入网场景的初步区分**（详见第 7 层）：
- 有 Beacon 但加入失败 → L1-2（Association 失败）而非本场景
- 有 Beacon 但加入了错误的网 → L1-7

---

## 2. 正常抓包基线

**健康流程**（加入设备视角，官方 network-steering.c 注释确认）：

```
[加入设备] Beacon Request ──单跳广播──> [范围内所有 15.4 设备]
    <── Beacon (PAN ID / EPAN ID / 栈特性 / PermitJoin 标志 / 子设备容量) ── [各设备响应]

Network Steering 全流程（官方 12 步）:
1. 用 Install Code 密钥（有则用，无则跳到 9）
2. 主信道掩码（默认 BIT32(11)|BIT32(14)）
3. 单信道 Active Scan → 收集 beacon
4. 过滤：permit join=0 的剔除 / stack profile≠2 的剔除 / 重复 PAN 剔除
5. 对每个发现的网络尝试加入
6. 重复 3-5 直到掩码内信道试完
7. 主信道全失败 → 次信道掩码（全信道）重试 3-6
8. 仍失败 → 换 ZigbeeAlliance09 密钥重试 2-7
9. 仍失败 → 换分布式密钥重试 2-7
12. 全部失败 → 返回失败给应用
```

**抓包基线特征**：
- **加入设备侧**：Beacon Request（MAC 命令帧 0x07，目标=广播 0xFFFF）→ 数个 Beacon 响应（可能来自多个 PAN）
- **网络侧**：被 request 触发的 beacon 响应（同一信道内即刻返回）
- **Beacon 响应时间：< 50ms（实测基线，见第 12 层）** — v1.0 曾写"< 1s"，实测响应延迟 3-48ms；1s 是"健康判定"的宽松上限，50ms 是正常区间。⚠️ v1.2 修订：多素材实测（标准入网抓包-2）median 67.8ms、正常响应可到 100ms+——50ms 偏严格，**1s 窗口才是可靠异常阈值**；延迟基线受网络负载/距离等环境因素影响（用户确认不同测试批次整体快慢不同）
- 响应数量：范围内每 PAN 至少 1 个（router/coordinator 各自响应；permit=0 的 PAN 也会响应 beacon request，跨 PAN 广播验证）
- **健康时 request→response 命中率 ≈ 100%**（实测 32/32 与 8/9）— ⚠️ v1.2 修订：射频环境不能按 100% 要求，**允许单次 MISS，判定 L1-1 需连续多次 request 无响应**（见第 4 层规则修正）

## 3. 异常表现

| 观察点 | 正常 | 异常（本场景） |
|--------|------|----------------|
| Beacon Request 发出 | 有（设备侧可见） | 有，但无任何响应 |
| Beacon 响应 | ≥1 个 | **0 个** |
| 设备侧状态 | EMBER_NETWORK_UP | `EMBER_NO_BEACONS` (0xAB) → `Network Steering Failed (0x94)` |
| 重试模式 | 找到网络即停 | 主/次信道全部扫完，换密钥策略重试，最终失败 |

**核心异常特征**：Beacon Request 发出后（设备侧可见或 sniffer 听到），**1 秒内无任何 Beacon 响应**，且覆盖全扫描流程。

## 4. 判定条件（可编程规则）

```
规则 L1-1-A（设备侧，高置信）— v1.2 修订（射频环境允许单次 MISS）:
  beacon_request_count >= 3               ← 至少 3 次 request（排除单次瞬态）
  AND consecutive_miss_count >= 2         ← 连续 2+ 次 request 在 1s 窗口内 0 响应
  → L1-1 命中
  单次 MISS 不判定（实测健康网络 8/9 命中率，见第 12 层）

规则 L1-1-B（网络侧，中/低置信）:
  beacon_request_count == 0 AND beacon_broadcast_flow 正常
  → 不可判定（可能是 sniffer 听不到 request，见第 8 层）

规则 L1-1-C（辅助，根因细分）:
  beacon_request_count > 0 AND beacon_response == 0
  AND 网络侧同信道有 beacon 广播 (beacon_pan_set 非空)
  → 根因: 信道不匹配 或 加入设备在范围外（beacon 广播说明网络存在）
```

**关键字段**：
- Beacon Request：MAC 帧类型=3（命令），命令 ID=0x07，目标地址=广播 (0xFFFF)
- Beacon 响应：MAC 帧类型=0，含 PAN ID / EPAN ID / PermitJoin / 容量位

## 5. 直接证据（铁证）

| 优先级 | 证据 | 说明 |
|--------|------|------|
| ★★★ | 设备侧 `EMBER_NO_BEACONS` (0xAB) 日志 | 协议栈级确认：扫描完成，无 beacon 可用。这是**设备视角**的铁证 |
| ★★★ | Beacon Request 后 1s 窗口内 0 响应（设备侧抓到） | 帧级确认：请求发出，无网络应答 |
| ★★ | 全扫描流程（主+次信道×多密钥策略）均无 beacon | 排除"单信道瞬态丢失"，是系统性无网络 |
| ★ | 同信道存在其他 PAN 的 beacon 广播但无响应 | 反向证明：网络在，但设备听不到它 / 它听不到设备（信道或距离） |

**证据定位建议**：入网操作触发时刻起，覆盖至少 30-60s（完整 steering 周期）。

## 6. 根因链路

```
表象: 设备无法入网，无 beacon 响应
  ├─ 直接原因 1: 信道不匹配（设备扫描掩码 ≠ 网络信道）
  │    └─ 深层: 设备配置的信道掩码错误 / 网络已切信道但设备未更新（关联 L4-1）
  ├─ 直接原因 2: 距离/射频（设备在网络范围外）
  │    └─ 深层: 发射功率低 / 天线问题 / 物理距离远（beacon request 单跳无法到达）
  ├─ 直接原因 3: 网络侧无 beacon 源
  │    └─ 深层: 协调器/路由器未上电 / 网络未形成 / permit join 期间节点均离线
  ├─ 直接原因 4: 干扰（beacon request 被淹没）
  │    └─ 深层: 2.4GHz 拥挤，CCA 持续失败（关联 L7-2）
  └─ 直接原因 5: 设备侧 stack 异常（扫描未实际执行）
       └─ 深层: 固件配置 / 天线开关未初始化（少见，需设备日志佐证）
```

## 7. 混淆项（长得像但不是）

| 混淆场景 | 抓包差异 | 排除方法 |
|----------|----------|----------|
| **L1-2 Association 失败** | beacon 有响应，但 Association Request 无 Response | 查 beacon 存在性 — 本场景 beacon=0 |
| **L1-7 误入错误 PAN** | beacon 有响应且加入了网，但 EPAN 不是目标网络 | 查加入后的 EPAN ID |
| **Beacon 有但 PermitJoin=0** | beacon 响应存在，但 Permit Join 标志=0（这是"网络拒绝新设备"，不是"发现失败"） | 解析 beacon 的 PermitJoin 位 |
| **L2-3 Orphan 重连失败** | 设备是已入网设备在找父节点（Rejoin Request 而非 Association） | 查设备网络状态/是否已分配短地址 |
| **sniffer 覆盖盲区误判** | 抓包无 beacon request 也无 beacon | 是盲区不是网络问题（见第 8 层） |

## 8. 自动检测盲区

| 盲区类型 | 本场景表现 | 后果 |
|----------|-----------|------|
| **sniffer 听不到** | 设备侧行为完全不可见（设备未发出/未收到请求均无帧） | 无证据 → 不可判定 |
| **抓包未覆盖** | 设备扫描的信道不在 sniffer 监听信道 | beacon request 在别的信道发出，完全不可见 |
| **设备未听到** | sniffer 听到 beacon 响应（网络侧），但加入设备实际没听到（距离/干扰） | "有响应"的抓包 ≠ 设备成功发现网络 → 不能排除 L1-1 |
| **时间窗口不足** | 只抓了几秒，steering 流程未完整覆盖 | 单信道瞬态无 beacon ≠ 系统无网络 |

**铁律**：本场景"无 beacon 响应"的结论**必须锚定到设备侧证据**（NO_BEACONS 日志或设备旁 sniffer 抓到的 request 无响应）。仅凭网络侧抓包，一律给"不可判定"或"低置信"。

**⚠️ 帧识别警示（二次审查教训）**：Beacon Request 的命令 ID（0x07）位于 MAC payload 首字节（需 scapy `Dot15d4Cmd.cmd_id` 或按地址模式解析偏移），**不是** `raw[1]`（那是 MAC 序列号）。本项目 v1.0 曾用 `raw[1]==0x07` 误判，导致"0 个 request"的错误结论 — 分析引擎实现时必须用协议解析器而非固定字节偏移。

## 9. 置信度分级

| 置信度 | 判定条件 | 复核建议 |
|--------|----------|----------|
| **高** | 设备侧 NO_BEACONS 日志 + 设备旁抓包：request 发出 0 响应 | 直接定位根因（信道/距离/干扰） |
| **中** | 仅设备侧日志（无设备旁抓包），无其他异常帧 | 需现场复核信道与范围 |
| **低** | 仅网络侧抓包推断（beacon 流正常但无入网活动） | 先补抓包（sniffer 移到设备旁），不要下结论 |
| **不可判定** | 抓包条件不满足（如 sniffer 不在设备旁且无设备日志） | 输出"需要补充数据"，给出补抓指引 |

## 10. 人工复核清单

- [ ] 确认加入设备的**扫描信道掩码**与网络信道一致（设备配置 vs 网络 beacon 信道）
- [ ] 确认**网络侧有 beacon 源**：协调器/路由器上电、网络已形成（网络侧抓包看 beacon 广播）
- [ ] 确认**物理范围**：加入设备是否在最近 router/coordinator 的单跳范围内（beacon request 不过路由）
- [ ] 确认**permit join 状态**（若 beacon 有响应但被拒 → 转 L1-2）
- [ ] 确认 2.4GHz 干扰（若设备侧持续 CCA 失败 → 转 L7-2）
- [ ] 设备侧日志复核：`NO_BEACONS (0xAB)` / `Network Steering Failed (0x94)` 出现次数与重试节奏

## 11. 上下游关联

| 关联 | 场景 | 关系 |
|------|------|------|
| 下游 | **L1-2 Association 失败** | beacon 发现了但 Association 失败 → 本场景的下一步 |
| 下游 | **L1-3 密钥分发失败** | Association 成功但无 Transport Key |
| 下游 | **L1-7 误入错误 PAN** | beacon 有多个，加入了错误的网络 |
| 同层 | **L4-1 信道切换未跟随** | 网络切信道后，未更新的设备表现为"找不到网络"（根因 1 的深层） |
| 同层 | **L7-2 CCA 信道接入失败** | 干扰导致 request 发不出 → 表象相同 |
| 修复指向 | — | 校正信道掩码 / 增加范围覆盖 / 确认协调器在线 / 检查干扰 |

## 12. 判定示例（真实抓包）

### 示例 A：健康基线（实测数据）— 反例，用于校准"正常"长什么样

**来源**：`D:\work\zigbee_capture\中继入网抓包(1).cubx`（8626 包，网络侧监听，scapy `Dot15d4` 解析）

**抓包统计**：
- **Beacon Request：32 个**（MAC 命令 0x07，目标=广播 0xFFFF）
- **Beacon 帧：1484 个**（MAC 帧类型 0）
- **Request 后 1s 内有响应：32/32（100%）**
- **响应延迟实测**：3ms ~ 48ms（如 req id=38 ts=...527.637 → 响应延迟 [3, 5, 15, 20, 23]ms）

**判定**：**健康网络**（非 L1-1）。request 全部有响应且响应极快 — 这是 L1-1 的**对照基线**：任何"request 发出后 >50ms 无响应"都应视为异常。

**用法**：分析引擎用此数据校准 L1-1 判定阈值 — 健康响应延迟 3-48ms，"1s 窗口"足够宽松。

**⚠️ 版本教训**：v1.0 曾将此包误判为"0 个 Beacon Request 的盲区案例"（帧识别错误），二次审查后完全反转。

### 示例 A2：健康基线（第二次实测，v1.2 新增）

**来源**：`C:\Users\Administrator\Desktop\zigbee_capture\1-标准入网抓包-2.cubx`（887 包，网络侧，scapy 解析）

**抓包统计**：
- **Beacon Request：9 个**，命中 **8/9（88.9%）** — 单次 MISS（#173 t=8.89s）无前后异常
- **响应延迟分布**：min=3.1ms, **median=67.8ms**, max=837.2ms（n=39）
- **跨 PAN 响应**：#232 含 0xDF59、#328 含 0x1F1D/0x1C1D（permit=0 也响应）
- 用户备注：本次入网测试整体比上次偏慢 — 延迟受测试环境（网络负载/距离）影响

**判定**：**健康网络**。验证了 v1.2 两项修正：
1. 命中率允许单次 MISS（8/9 仍健康）
2. "50ms 正常区间"偏严格（median 67.8ms）— **1s 窗口是可靠异常阈值**，50ms 仅供参考

### 示例 B：（待补）真实 L1-1 故障包

**条件**：加入设备旁的抓包，完整 Network Steering 周期。
**预期特征**：Beacon Request（`MAC Cmd 0x07`）发出后 50ms-1s 内 0 响应 → 主/次信道全扫（多信道 request 序列）→ 设备停止尝试。按 v1.2 规则：**连续 2+ 次 request 无响应**才判定。
**判定**：高置信 L1-1。
**候选素材**：`D:\work\zigbee_capture\入网后又离网问题分析示例包.cubx`（1932 包）待验证 — 若含入网阶段 request 无响应则为 L1-1，若 request 有响应则排除。
