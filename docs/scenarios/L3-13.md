# 场景 L3-13：广播中继失败 (Broadcast Relay Failure)

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L3 运营期核心 | 状态：**v1.0 文档层（用户裁定: 检测器等日志素材）**
> 官方依据（Silicon Labs）：
> - [sl_status.h 状态码定义](https://github.com/SiliconLabs/simplicity_sdk/blob/sisdk-2025.6/platform/common/inc/sl_status.h)：`SL_STATUS_ZIGBEE_BROADCAST_TO_SLEEPY_CHILDREN_TIMEOUT (0x0C27)` = "Broadcast message timeout while waiting for sleepy children to poll"; `SL_STATUS_ZIGBEE_BROADCAST_RELAY_FAILED (0x0C28)` = "**Expected a neighbor to relay the message, but none did**"
> - [error-def.h](https://github.com/SiliconLabs/gecko_sdk/blob/gsdk_4.5/protocol/zigbee/stack/include/error-def.h)（旧命名 EMBER_BROADCAST_RELAY_FAILED = 0xD1, 7.5 引入更细粒度状态）
> - [EmberZNet 堆栈重试 KBA](https://community.silabs.com/s/article/emberznet-cn-x)（广播机制: 无 MAC ACK; NWK 监听邻居转播作被动确认, 未转播则 500ms 重发, 共 4 次尝试）
> - [社区 FAQ: 广播到睡眠节点缓冲满](https://community.silabs.com/s/article/what-does-a-parent-do-when-it-has-no-more-room-to-buffer-messages-for-sleepy-chi)（"Since broadcasts are unreliable, there's no guaranteed way to know that your broadcast was dropped"）
> ⚠️ **状态声明**：**核心约束 — 0xC27/0xC28 是栈内部 sl_status_t 状态 (messageSentHandler/stackStatusHandler 回调), 不上空口, 抓包不可见, 需网关日志**; 抓包侧仅有代理信号 (广播重发/转播缺失), 且素材语义未明 (实测 0.03s 快速重发 ≠ 官方 500ms 重试) — 检测器规则待日志素材/现场确认后落地

## 0. 抓包可行性（数据现实层）— ⚠️ 核心受限

| 条件 | 要求 | 说明 |
|------|------|------|
| **0xC27/0xC28 直接证据** | ❌ **抓包不可见** — 栈内部状态 (messageSentHandler/stackStatusHandler 回调), 不上空口 | 需**网关日志** (与 0x66 DELIVERY_FAILED 同类); 检测器 R3 待日志素材 |
| **广播帧可见性** | ✅ 素材实测: 广播帧丰富 (中继 1927 / test2 5567) | 广播 = NWK dst ≥ 0xFFF0 |
| **广播重发 (代理信号)** | ⚠️ 语义未明: 官方 NWK 重试 500ms×4 次; 素材实测**中位 0.03s 快速重发** (中继 902 对真实重发) — 非官方重试模式 | 0.03s 重发语义待现场确认 (广播风暴/应用层连发?) — 不能套官方机制解释 |
| **转播缺失 (代理信号)** | ❌ 单抓包器覆盖约束 (群控教训: "不转发"高概率是漏抓假象) | 邻居转播不可见 ≠ 没转播 — 不可判定 |
| **广播到睡眠节点** | ❌ 官方: 失败无通知 ("no guaranteed way to know") | 0xC27 超时仅发送方栈内知晓 |

**结论**: 本场景的**协议级铁证 (0xC27/0xC28) 在网关日志**, 抓包只能提供弱代理信号 — 第 9 层置信度必须反映此约束。

## 1. 场景识别（入口）

**用户描述关键词**：`广播控制不到设备`、`群控部分设备没反应`、`广播没扩散`、`中继不转广播`、`广播风暴`

**典型症状**：
- 网关发广播 (群控/场景联动), 部分设备无响应 (远端/经中继的设备)
- 网关日志: `EMBER_BROADCAST_RELAY_FAILED (0xD1)` / `SL_STATUS_ZIGBEE_BROADCAST_RELAY_FAILED (0x0C28)` — "期望邻居转播但没人转"
- 网关日志: `0xC27` 广播等睡眠子设备 poll 超时
- 抓包: 同一广播帧快速重复出现 (发送方反复尝试)

**与相邻场景的区分**：
- 单播命令失败 → **L3-1/L3-5**（单播路由体系）
- 广播后设备无响应但广播已扩散 → 设备应用层（L3-2/睡眠）
- 中继完全掉线 → **L2-4**（路由器掉线连锁）；本场景是中继**在**但不转广播

---

## 2. 正常抓包基线 — ✅ 官方流程确认

```
广播机制 (官方 KBA):
① 发送方 NWK 广播 (nwk_dst=0xFFFF/0xFFFC, 无 MAC ACK — 广播不请求链路确认)
② 邻居收到 → 转播 (rebroadcast) — 转播是"被动确认" (passive ack): 发送方听邻居转播
   来确认扩散成功
③ NWK 检查邻居表中所有邻居是否转播 / MAC 报告失败
④ 未转播 → 500ms 后重发, 共 4 次尝试 (每次尝试间 500ms)
⑤ 全部邻居都转播 → 广播完成
```

**正常抓包特征**: 广播帧发出后, 邻居路由器在数 ms-数百 ms 内转播 (同 nwk_seq, nwk_src=转播者); 无重复发送 (一次扩散成功)。test2 大网络实证: 767/5567 广播有邻居转播。

## 4. 判定条件（可编程规则）— 框架 (检测器待日志素材)

```
R1 广播重发 (代理信号, 待素材语义确认):
    同 (nwk_src, nwk_seq, 广播地址) 短窗口内重复出现 (mac_seq 不同 = 真实重发,
    排除抓包器物理重复) → "发送方未获邻居转播"候选
    ⚠️ 素材实测: 重发间隔中位 0.03s (非官方 500ms) — 语义未明, 阈值待现场确认

R2 转播缺失 (代理信号, 弱):
    广播发出后, 预期转播者 (Link Status 邻居) 未转播同 seq 广播
    ⚠️ 单抓包器覆盖约束: 转播不可见 ≠ 没转播 (群控教训) — 不可判定为主

R3 栈内状态 (铁证, 待日志素材):
    网关日志 0xC27 (广播等睡眠子设备超时) / 0xC28 (期望邻居转播但没人转)
    → 铁证级 (抓包不可见, 需日志解析器)
```

**判定参数**（待素材校准）:
- R1 重发窗口/间隔阈值 — 素材 0.03s 语义未明, **不能直接套官方 500ms**
- R2 转播匹配窗口 (官方无明确值; 转播在数 ms-数百 ms)
- R3 日志解析 — 待网关日志格式

## 6. 根因链路 — [官方确认]

```
广播中继失败 (0xC28: 期望邻居转播但没人转)
├─ 邻居路由器全部失聪/掉线: 中继物理层不在 (→ L2-4/L3-9 交叉)
├─ 邻居路由器广播表溢出/队列满: 收到但无法转播 (官方: 广播表满丢弃)
├─ 邻居路由器 CCA 持续失败: 想转播但信道忙 (官方 KBA: CCA 失败重试)
├─ 干扰/瞬时噪声: 广播无 ACK 无重传保证, 单次扩散失败即重发
广播到睡眠子设备超时 (0xC27)
├─ 子设备睡眠周期 > 广播等待窗口 (官方: 等 poll 超时)
└─ 父节点间接队列满 (官方 FAQ: 广播到睡眠子设备只跟踪最近一条, 旧的被替换)
```

## 7. 混淆项（长得像但不是）— [骨架]

| 混淆项 | 区分 |
|--------|------|
| 应用层周期性广播 (轮询) | 不同 payload/新 seq — 同 (src,seq) 短窗口重复才是重发 |
| seq 回绕 (8 位, 长抓包) | 同 (src,seq) 长间隔 (>2s) = 回绕后新广播, 非重发 |
| 抓包器物理重复 | mac_seq 相同 = 同一帧抓两次 (群控教训: 37% 重复) — 排除 |
| 广播风暴 (应用层高频广播) | 不同 seq 高频广播 — 非单帧重发 (0.03s 快速重发语义待确认) |
| 单播失败 (L3-1/L3-5) | 单播有路由/ACK 体系, 广播无 — 判定体系不同 |
| 中继掉线 (L2-4) | 中继彻底不在 (Leave/邻居消失) vs 在但不转广播 |

## 8. 自动检测盲区 — [官方确认, 本场景重点]

1. **铁证不可抓**: 0xC27/0xC28 是栈内部状态 (messageSentHandler/stackStatusHandler 回调), 不上空口 — 检测器必须依赖**网关日志** (R3)
2. **转播缺失的 sniffer 盲区**: 单抓包器只见自己射频范围内的转播 — "没看到转播" ≠ "没转播" (群控压测实证教训: "中继不转发"是漏抓假象)
3. **广播到睡眠节点无通知**: 官方 FAQ 明确 "no guaranteed way to know that your broadcast was dropped" — 睡眠节点广播丢失可能完全不可见
4. **重发语义未明**: 素材实测 0.03s 快速重发 (非官方 500ms 重试模式) — 代理信号的解释需现场确认
5. **广播表满丢弃不可见**: 邻居收到但广播表满丢弃 — 发送方看到"没人转播", 实际是邻居内部丢弃 (官方: 广播表满)

## 自审记录 (2026-08-13)

1. **核心约束确认 (MCP)**: 0xC27/0xC28 是 sl_status_t 栈内部状态 (messageSentHandler/stackStatusHandler), 不上空口 — 抓包不可见, 铁证在网关日志。taxonomy 写 "0x0C28 BROADCAST_RELAY_FAILED" 未声明可见性, 文档已补 (第 0/5/8 层)。
2. **代理信号语义未明**: 素材广播重发中位 0.03s ≠ 官方 500ms NWK 重试 — 不硬套官方机制 (不妄加判断), 检测器规则待现场确认 (用户裁定: 先文档层)。
3. **物理重复 vs 真实重发区分**: mac_seq 相同 = 抓包器重复 (仅 1 对); 902 对为真实重发。
