## 实现要点 (总控设计)

### 1. 后端 — backend/api/topology.py /api/topology/graph 节点数据扩展
- 每节点加: `model_id` / `manufacturer_name` (从 /api/nodes 同源聚合或 graph 内计算 —
  建议 graph 构建时复用 nodes 聚合逻辑, 避免双份)
- 每节点加行为状态: `behavior`: 遍历 full_packets (或 packets) 时间窗:
  - rejoin/入网事件 (nwk_cmd_id in (6,7) 或 Device Announce) → "rejoining"
  - 终端设备 (device_type=end_device) 且窗内无 poll (mac_cmd_id=4) → "sleeping"
  - 窗后段 (末 25% 时间) 无该节点任何帧且之前有 → "offline"
  - 否则 "active"
  - poll 间隔: 该节点 poll 帧 ts 差值中位数 (或最近间隔)
- 注意时间窗: 是否与 topoT0/T1 过滤一致 (无过滤=全量)

### 2. 前端 — frontend/js/topo.js
- **label 第二行型号**: style label 支持多行 (text-wrap); 节点 data.model_id 非空 →
  `label: 地址\n型号` (font-size 8px 灰)
- **行为状态样式**: sleeping → opacity 0.55; rejoining → border-color #f59e0b + 虚线;
  offline → 角标 (border 红); active 默认
- **tooltip 增强**: mouseover 信息补: EUI64 (mono 小字)、厂商/型号、状态文字
  (活跃/休眠/重连中/离线)、poll 间隔 (终端时)、帧量 (收/发 — 若 graph 数据有)、LS 邻居数 (已有)
- 不动: 布局/形状分类/图例/边样式 (U13 单独处理链路)

### 3. 联动注意
- U13 (链路证据重构) 与 U14 (节点显示) 均动 topo.js — **两个实现窗口需串行或协调**,
  建议 U13 先、U14 后 (链路是结构, 节点是呈现); 若并行, 分别独立文件段改动并提前沟通
- time 过滤 (topoT0/T1) 时行为状态按窗内重算 (与滑块联动)

## 风险

- 多行 label 可能挤压节点 (协调器大六边形 60px 应容纳; 终端小圆 22px 可能放不下 —
  小节点型号显示不全用 tooltip 兜底)
- 状态判定与时间窗耦合: 无过滤时全量计算, 状态是"全程"语义; 有过滤时是"窗内"语义 —
  需明确并展示一致
- offline 判定边界 (末 25% 无帧) 需素材校准, 宁缺勿滥 (标 unknown 也行)
- 与 U13 并发时 topo.js 冲突 — 按上节协调
