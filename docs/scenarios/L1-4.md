# 场景 L1-4：TC 拒绝入网 / 运营期踢人（Trust Center Deny）

> 模板：ADR-0002 场景拆解模板（14 层）| 分类：L1 网络形成与入网 | 状态：**v1.2（官方依据 + 素材实证 + 自审修正：R2b 高置信验证通过；R1/R2a/R3 故障态待素材）**
> 官方依据：Silicon Labs 文档 + SDK 源码（链接见各层）：
> - TC deny 三选一：`docs.silabs.com Zigbee Security Concepts`（发 NWK Key / Remove Device / 忽略后 2s 静默移除）
> - 拒绝流程：`Standard Security`（Assoc 成功 → parent 发 Update Device → TC 决策 → 拒绝则 Remove Device 给 parent）
> - Remove Device 命令：`trust-center.h` `sl_zigbee_send_remove_device()`（APS 加密、仅 TC 可发、ED 目标发给 parent）
> - TC 决策枚举：`ember-types.h` `EmberJoinDecision`（EMBER_DENY_JOIN=2）与 `EmberDeviceUpdate`（0=secured rejoin, 1=unsecured join, 2=device left, 3=unsecured rejoin）

## 0. 抓包可行性（数据现实层）— ✅ 已确认

| 条件 | 要求 | 说明 |
|------|------|------|
| **最小抓包时长** | 从 Assoc 成功前开始抓（覆盖 Update Device → TC 决策窗口） | TC 决策在 Assoc 后立即发生（密钥窗口实测 1.32s 内，拒绝发生在 TransportKey 之前） |
| **sniffer 位置** | 网络侧即可；若被踢设备经中继接入，需覆盖 TC→中继 链路 | Remove Device 是 TC→parent 单播；多跳场景 parent=中继（可能经源路由转发） |
| **捕获信道** | 与网络信道一致 | — |
| **命令帧可见性** | **✅ 实测：APS 命令 ID 可直接观测**（无需解密配置，同 L1-3 的 0x05/0x08/0x0F/0x10） | Remove Device (0x07) 同为 APS 命令帧 |
| **Remove Device target 盲区** | 0x07 的 ID 可见；**target EUI64 已提取**（v1.2: `aps_cmd_remove_target`, cubx/tshark 两路实现） | 路由器被踢时 dst=自身，无需 target 也能判定；ED 经 parent 被踢时 dst=parent，**target→短地址映射未实现** [待增强] |
| **Mgmt Leave Req 可见性** | **✅ 素材实证可见**：ZDP cluster 0x0034 明文可读（leave_question 抓到 12 条） | R2b 判定不依赖解密；单跳直达 TC 场景即可见 |
| **静默拒绝盲区** | 官方 ignore 路径**无线帧可抓**（parent 2s 后静默移除） | R3 只能靠"缺失帧"推断 → 中/低置信 |

## 1. 场景识别（入口）

**用户描述关键词**：`TC 拒绝`、`DENY_JOIN`、`拒绝入网`、`不让加入`、`被踢`、`踢设备`、`拉黑`、`Remove Device`、`remove device failed`、`入网后被移除`、`白名单`、`设备被移除`

**典型症状**：
- 设备 Association 成功（AssocResp status=0x00）但**从未收到 NWK Key**，随后被移除或静默消失
- 设备已入网正常运行，**突然被 TC 移除**（运营期踢人，如 leave_question 的 0xCBEB）
- 设备侧日志：`EMBER_DENY_JOIN` / `Remove device` / 收到 Remove Device 后 Leave
- TC 侧：`Trust Center Join Handler: decision = deny join`

**与相邻场景的区分**（详见第 7 层）：
- Assoc 本身失败 → **L1-2**
- Assoc 成功 + 拿不到/验证不了密钥 → **L1-3**（无 0x07！TC 想给 key 但给不出/设备解不出）
- 密钥流程完整 + 正常通信 → 排除本场景

## 2. 正常抓包基线 — ✅ 官方流程确认

**TC 允许入网**（集中式安全网络，标准安全模式）：
```
① MAC Assoc (AssocReq→AssocResp status=0x00)
② (parent→TC) Update Device (0x06, status=1 UNSECURED_JOIN)   ← TC 决策入口
③ TC→parent Transport Key (0x05, key_type=0x01 NWK Key, 用设备 Link Key 加密)
④ 设备 Device Announce (0x0013, 广播)   ← 已入网认证完成
⑤ 后续密钥流程 (Request Key 0x08 / Transport Key TCLK 0x05 / Verify 0x0F / Confirm 0x10) — 同 L1-3
```
> 官方来源：docs.silabs.com Standard Security「Joining a Network」「Trust Center Decision Process Summary」。
> 官方原文：*"After sending the success response to the MAC association request, the router sends the trust center an Update Device message indicating that a new node wishes to join... If the device is not allowed to join, a Remove Device request is sent to the parent."*

**TC 三选一**（官方原文，Concepts「Trust Center Networks」）：
1. 发 NWK Key（parent 转发给设备）→ 允许入网
2. **发 Remove Device 命令给 parent** → 显式拒绝（本场景 R1/R2）
3. **忽略请求** → *"Parents will silently remove the device from the network if it does not receive a network key within 2 seconds"*（本场景 R3）

**健康基线实测参考**（1-标准入网抓包-2, 0x2951）：无 0x07、密钥流程完整（0x05→0x08→0x05→0x0F→0x10）、全包 0 条 Leave — 健康对照（L1-3.md 第 2 层，本场景复用）。

## 3. 异常表现 — [官方确认，R1/R3 帧序列待素材]

| 观察点 | 正常（允许入网） | 异常（本场景） |
|--------|------------------|----------------|
| AssocResp | status=0x00 | status=0x00（Assoc 成功！） |
| Update Device (0x06, parent→TC) | ② 出现 | 出现（触发 TC 决策）— 单跳直连 TC 时可能不可见 |
| **Remove Device (0x07, TC→parent)** | **缺失** | **出现 = 铁证（显式拒绝, R1/R2a）** |
| **Mgmt Leave Req (0x0034, TC→设备)** | 缺失 | **出现 = ZDO 踢人指令（R2b, 素材实证）** |
| Transport Key (0x05, NWK) | ③ 出现 | **缺失**（被拒/被忽略 — 与 L1-3-A1 帧级重叠） |
| Device Announce | ④ 出现 | **缺失**（入网拒绝 R1）；或**曾经出现**（运营期踢人 R2a/b/c 的前置） |
| NWK Leave | 无 | 设备收到 Remove Device 后 Leave（rejoin 标志随设备策略）；或静默消失（R3） |
| 设备侧 | 正常通信 | `EMBER_DENY_JOIN` 日志 / 收到 remove 后 Leave |
| TC 侧 | 无动作 | `Trust Center Join Handler: decision = deny join (02)` 日志 |

**R1 vs R2 帧级分界**（不依赖时间窗口，用入网状态判）：
- **R1 入网拒绝**：0x07 出现 + 该设备**从未完成入网**（无 TransportKey(NWK)、无 Announce）
- **R2a 运营期踢人-APS 指令**：0x07 出现 + 设备**已入网**（此前有 TransportKey(NWK) 或 Announce）
- **R2b 运营期踢人-ZDO 指令**：Mgmt Leave Req (0x0034, TC→设备) 出现 — 素材实证形态（leave_question 0xCBEB，TC 踢人指令 ×12 可见）
- **R2c 运营期踢人-响应帧**：无前置指令帧，但设备已入网 + 广播 Leave (rejoin=0) — 中置信（指令帧可能在 sniffer 盲区）

## 4. 判定条件（可编程规则）— 规则框架已确认（grilling 定稿 2026-08-04），R1/R3 阈值待素材

```
规则 L1-4-R1（入网阶段显式拒绝, 高置信, 官方流程确认）:
  remove_device (0x07) 出现 (TC→设备或 TC→parent)
  AND 目标设备未完成入网 (无 transport_key_nwk 0x05/key_type=0x01, 无 device_announce)
  → L1-4 命中 (根因: TC 安全策略拒绝 / install code 无 transient key / TC 无设备 link key)
    官方路径: trust-center.h EMBER_DENY_JOIN(2) → sl_zigbee_send_remove_device
              af-trust-center.c pre_join_callback: install code 查无 → DENY_JOIN

规则 L1-4-R2a（运营期踢人-显式, 高置信, 官方机制确认）:
  remove_device (0x07) 出现
  AND 目标设备已入网 (此前有 transport_key_nwk 或 device_announce)
  → L1-4 命中 (根因: 应用层决策踢设备 / TC 策略变更 — 白名单移除 / 拉黑)
    官方路径: sl_zigbee_send_remove_device (EZSP 0x00A8) — APS 认证, 设备无法忽略
    【v1.2】R2 拆三: R2a (0x07) / R2b (Mgmt Leave Req) / R2c (广播 Leave 响应)

规则 L1-4-R2b（运营期踢人-ZDO 指令型, 高置信, 素材实证 2026-08-04）:
  mgmt_leave_req (ZDP cluster 0x0034, src=TC 0x0000, 单播给设备) 出现
  → L1-4 命中 (根因: TC 应用层通过 ZDO Mgmt Leave Req 指令设备离开)
    素材实证: leave_question 0xCBEB — TC 发 Mgmt Leave Req ×12 (t=1785138818.0-19.4)
    与设备广播 Leave ×3 (t=1785138818.4-19.4) 交织 → R2b 高置信命中
    【v1.2 修正】v1.0/v1.1 声称"TC 指令帧抓不到"是错误断言 — 本素材 TC 踢人指令
    (Mgmt Leave Req) 完全可见! 实际踢人路径是 ZDO Mgmt Leave Req, 不是 APS 0x07。
    自审记录: 首次分析只解析了 0x07, 未解析 ZDP 0x0034, 把"没解析"误当成"抓不到"。

规则 L1-4-R2c（运营期踢人-响应帧型, 中置信, 素材实证 2026-08-04）:
  设备已入网 (有 transport_key_nwk 或 device_announce)
  AND 设备广播 Leave (nwk_dst=0xFFFD, src=设备, rejoin=0/request=0)
  AND 无前置指令帧 (无 0x07, 无 Mgmt Leave Req)
  AND 无密钥验证失败上下文 (无 tclk 分发后 verify/confirm 缺失 — 否则归 L1-3-B2)
  → L1-4 命中 (根因: 疑似运营期踢人 — 设备广播 Leave Announcement (Silabs KB:
    设备执行 Leave 时广播); 指令帧 (0x07/Mgmt Leave Req/单播 Leave) 未被 sniffer 捕获,
    或设备被 child 表移除后自行离网)
    注意: 设备自愿永久离网 (rejoin=0, request=0 广播) 与 R2c **帧级相同** — 无法仅靠
    本帧形态区分, 前置指令帧 (R2b) 或设备日志是唯一区分途径
    【v1.2 拆分】原 v1.1 R2b (广播 Leave) 降为 R2c; 原 R2b 让位给 Mgmt Leave Req 指令型

规则 L1-4-R3（静默拒绝, 中置信, 官方 ignore 路径确认）:
  assoc_resp.status == 0x00
  AND 无 remove_device (0x07)                            ← TC 未显式拒绝
  AND 无 transport_key_nwk (0x05, key_type=0x01)         ← TC 忽略, 未发 key
  AND 无 device_announce                                 ← 设备无 NWK Key, 发不出
  AND 设备消失/重试 Assoc/Leave                          ← parent 2s 静默移除 (官方原文)
  → L1-4 命中 (R3) 且 **与 L1-3-A1 双报** — 帧级不可分:
    R3 = TC 策略上 ignore (如 well-known key rejoin 建议静默拒绝);
    A1 = TC 想发但配置错误/帧丢失 (EMBER_KEY_NOT_AUTHORIZED);
    → 判定提示 "需 TC/设备日志仲裁" (TC 日志: deny/ignore vs 加密失败; 设备日志: 0x0C1B)

规则 L1-4-EX（排除）:
  remove_device (0x07) 缺失
  AND (transport_key_nwk 出现 或 device_announce 出现)
  → 排除 L1-4 (TC 允许入网, 密钥流程正常 → 归 L1-3-C / 健康)
```

**关键字段**（官方确认）：
- Remove Device：APS cmd 0x07；payload = target EUI64 (deviceToRemoveLong)；`sl_zigbee_send_remove_device(destShort, destLong, deviceToRemoveLong)` — **dest 是 parent**（ED 场景 dest ≠ target；router 场景 dest = target）；APS 加密（用 destination 的 link key）
- Update Device：APS cmd 0x06；payload status：1=UNSECURED_JOIN（新设备加入）、0=SECURED_REJOIN、3=UNSECURED_REJOIN、2=DEVICE_LEFT（设备离网通知）
- TC 决策枚举：EMBER_USE_PRECONFIGURED_KEY=0 / EMBER_SEND_KEY_IN_THE_CLEAR=1 / **EMBER_DENY_JOIN=2** / EMBER_NO_ACTION=3 / EMBER_ALLOW_REJOINS_ONLY=4

## 6. 根因链路 — [官方部分确认]

```
表象: Assoc 成功但没拿到 key / 已入网设备被移除
  ├─ 直接原因 1: TC 策略显式拒绝入网 → Remove Device (0x07) 给 parent → 规则 R1
  │    ├─ 深层: 应用层 join 策略 deny (白名单/黑名单, EUI64 过滤)
  │    ├─ 深层: install code 模式, TC transient key 表无该设备 → af-trust-center.c DENY_JOIN
  │    └─ 深层: TC 未配置全局 link key → 默认 handler DENY_JOIN (trust-center.h 官方注释)
  ├─ 直接原因 2: TC 应用层踢已入网设备
  │    ├─ 2a: Remove Device (0x07) → 规则 R2a (APS 认证, 高)
  │    ├─ 2b: Mgmt Leave Req (ZDP 0x0034) → 规则 R2b (ZDO 指令, 高) ← 素材实证路径
  │    ├─ 2c: 其他指令 (单播 NWK Leave) 或指令帧盲区 → 规则 R2c (广播 Leave 响应, 中)
  │    ├─ 深层: 用户/平台操作 (踢设备) / 策略变更 / 设备违规
  │    └─ 素材: leave_question 0xCBEB (入网→正常→被踢; TC 发 Mgmt Leave Req ×12)
  ├─ 直接原因 3: TC 静默忽略入网请求 → 无帧, parent 2s 静默移除 → 规则 R3
  │    ├─ 深层: well-known link key rejoin 被静默拒 (官方建议, 保兼容)
  │    ├─ 深层: TC 忙 / TC 侧安全处理失败
  │    └─ ⚠️ 与 L1-3-A1 (TC 未分发) 帧级不可分 — 需日志仲裁
  └─ 直接原因 4: (排除) 密钥验证失败被踢 → NWK Leave rejoin=0, **无 0x07** → L1-3-B2
       └─ 官方: network-creator-security VERIFY_KEY_FAILURE → emberLeaveRequest — 不是本场景
```

## 7. 混淆项（长得像但不是）— [骨架]

| 混淆场景 | 抓包差异 | 排除方法 |
|----------|----------|----------|
| **L1-3-A1 密钥未分发** | 无 0x07 + 无 0x05(NWK) + 无 Announce + 设备重试/Leave — **与 R3 帧级相同** | 帧级**不可分** → 双报 + 需 TC/设备日志仲裁（TC 日志 deny/ignore vs 加密失败；设备日志 0x0C1B） |
| **L1-3-B2 TC 踢人** | 无 0x07/Mgmt Leave Req；TCLK 已分发但 Verify/Confirm 缺失 + TC 发 NWK Leave (0x04, rejoin=0) | **帧级区分: 密钥验证失败上下文**（tclk + verify/confirm 缺失）→ R2c 排除逻辑；设备日志 `Key verification failed` |
| **设备自愿永久离网** | 设备广播 Leave (rejoin=0, request=0) — **与 R2c 帧级相同** | 靠**前置指令帧**（0x07/Mgmt Leave Req → R2a/R2b 高置信）或设备日志区分；无指令帧 → R2c 只能"疑似"（中置信） |
| **设备暂离/重入网** | 广播 Leave rejoin=1（离开后会重入） | rejoin=1 → 排除 R2b/R2c（非永久离开） |
| **L1-3 密钥流程完整但设备主动离网** | 0x05→0x08→0x05→0x0F→0x10 完整 + 设备主动 Leave (request=1) | 无 0x07/Mgmt Leave Req + 密钥流程完整 + Leave request=1 |
| **L1-2 Association 失败** | AssocResp status≠0x00 | 本场景 Assoc 成功 |
| **L1-5 大网络多跳入网失败** | Update Device 来自 >1 跳，TC 无 EUI64 解析 → APS 解密失败 | L1-5 无 0x07（TC 想发 key 但解不出）；L1-4 有 0x07（TC 明确拒绝） |
| **preconfigured NWK Key 场景** | 无 0x05(NWK) 但 Announce 出现 + 正常通信 | 规则 L1-3-A'：有 Announce = 已入网 ≠ 被拒 |

## 8. 自动检测盲区 — [官方确认]

| 盲区类型 | 本场景表现 | 后果 |
|----------|-----------|------|
| **Remove Device 发给中继 parent** | 0x07 是 TC→parent 单播；多跳场景（如 838D 经 1885 中继）可能经源路由转发，单 sniffer 覆盖不到 TC↔中继链路则抓不到 | 多跳入网拒绝素材需网络侧多位置或网关侧抓包 |
| **静默拒绝无帧可抓** | 官方 ignore 路径只有"缺失帧"（无 0x07/0x05/Announce）+ 设备消失 | R3 只能推断，中/低置信，必须与 L1-3-A1 双报 |
| **Remove Device target 映射** | target EUI64 已提取（`aps_cmd_remove_target`），但 **target→短地址映射未实现** | ED 被踢（0x07 发给 parent）设备级匹配失败 — 事件会展示在 remove_events 列表，但设备卡片不归因 [待增强] |
| **Remove Device 内容盲区** | 0x07 的 ID 可见，payload（target EUI64）是否可解取决于 sniffer 是否持 TC Link Key（APS 加密） | 判定流程不受影响（命令 ID 即可判定 R1/R2） |
| **R1/R2 分界的瞬态** | 设备刚 Assoc 成功尚未 Announce 即被踢（正常策略）vs 拒绝（R1） | 用"是否曾入网"（0x05/Announce 有无）判，避免误分 |

---

## 9. 置信度分级 — [框架确认]

| 置信度 | 判定条件 | 复核建议 |
|--------|----------|----------|
| **高** | R1/R2a：Remove Device (0x07) 出现 + 设备入网状态明确；R2b：Mgmt Leave Req (0x0034, TC→设备) 出现 + （可选）TC/设备侧日志 deny join | 直接定位根因（TC 策略/白名单/install code/应用层移除操作） |
| **中** | R2c：已入网设备广播 Leave (rejoin=0) 无前置指令帧（无法排除自愿离网）；R3：静默拒绝（无 0x07/0x05/Announce + 设备消失），与 L1-3-A1 双报 | R2c：查 TC 移除记录/设备日志仲裁；R3：查 TC 日志（deny vs ignore）与设备日志（0x0C1B 等） |
| **低** | 仅看到被踢 Leave（kicked 型）无指令帧上下文 | 补抓包（覆盖 TC 决策窗口）；查 TC 侧移除记录 |
| **不可判定** | 抓包未覆盖 Assoc 或 TC 决策窗口 / sniffer 不在 TC↔parent 链路上 | 需重抓 |

## 10. 人工复核清单 — [框架确认]

- [ ] AssocResp status 是否 0x00（确认不是 L1-2）
- [ ] **Remove Device (0x07) 是否出现** — 出现即 TC 显式拒绝（R1/R2）
- [ ] 0x07 的目标设备是谁（target EUI64，需解析器支持）：路由器看 dst；ED 看 payload
- [ ] 目标设备是否曾入网（TransportKey(NWK) / Announce 有无）— 区分 R1（未入网）vs R2（已入网）
- [ ] 无 0x07 时：是否无 0x05(NWK) 无 Announce + 设备消失 → R3，与 L1-3-A1 双报，需日志仲裁
- [ ] TC 侧日志：`Trust Center Join Handler: decision = deny join` vs `ignore`
- [ ] 设备侧日志：`EMBER_DENY_JOIN` / `0x0C1B NO_NETWORK_KEY_RECEIVED`（指向 L1-3-A1 而非 R3）
- [ ] 踢人动因：白名单/黑名单变更？install code 未登记？TC 无 link key？应用层手动移除？
- [ ] 排除 L1-3-B2：被踢但有密钥验证失败上下文（无 0x07，有 0x0F/0x10 缺失 + Leave rejoin=0）

## 11. 上下游关联 — [骨架]

| 关联 | 场景 | 关系 |
|------|------|------|
| 上游 | **L1-2 Association 失败** | Assoc 成功是进入本场景的前提 |
| 上游 | **L1-1 发现失败** | Beacon 正常是入网的前提 |
| 同层 | **L1-3 密钥分发失败** | 拒绝在密钥分发前（0x07 替代 0x05）；L1-3 无 0x07（TC 想给 key） |
| 同层 | **L1-3-B2 TC 踢人** | 运营期踢人的另一路径：NWK Leave rejoin=0 无 0x07（密钥验证失败） |
| 同层 | **L1-5 大网络多跳入网失败** | TC 收到 Update Device 但无法解密（无 EUI64 解析），非显式拒绝 |
| 修复指向 | — | TC join 策略核查（白名单/黑名单/install code 登记）/ TC link key 配置 / 应用层移除操作审计 |

## 12. 判定示例（真实抓包）— 示例 B ✅ R2 素材验证中 / 示例 A/C 待素材

### 示例 A：（待补）规则 R1 — 入网阶段显式拒绝

**条件**：AssocResp 成功 + Remove Device (0x07) 出现 + 设备无 TransportKey(NWK)/Announce（未入网）。
**候选素材**：需复现（TC 白名单 deny / install code 未登记）。

### 示例 B：规则 R2b — ZDO 指令型运营期踢人 ✅（leave_question_packet.pcap, 0xCBEB 路由器, 2026-08-04 素材实证 + v1.2 自审修正）

**素材状态**：早期问题素材，**已用当前解析器 (tshark 权威解析) 完成复核**。

**实测帧序列**（v1.2 复核，含 ZDP 层解析）：
```
t=1785138810.5  0xCBEB Device Announce ×4                       ← 0xCBEB 已入网 (路由器)
t=1785138804.4  0xCBEB → 0xFFFD 广播 Leave ×3 (rejoin=0, request=0)  ← 第一波 (无前置指令帧可见)
t=1785138818.0  0000 → 0xCBEB Mgmt Leave Req ×12 (ZDP 0x0034)    ← TC 踢人指令 (可见!)
t=1785138818.4  0xCBEB → 0xFFFD 广播 Leave ×3 (rejoin=0, request=0)  ← 第二波 (与指令交织)
全素材 Remove Device (0x07): 0 帧
→ 规则 L1-4-R2b 命中 (检测器实证: L1-4_HIT, R2b, 高置信, mgmt_leave_req=12)
```

**素材实证结论（2026-08-04, v1.2 修正）**：
1. **帧方向修正**：6 条 Leave 全部是 **0xCBEB 主动发广播**（src=0xCBEB, dst=0xFFFD）——设备侧的
   Leave Announcement（官方：设备执行 Leave 时广播）。早期 CONTEXT.md 记录 "协调器命令 0xCBEB
   离开" 是推断，帧方向不支持（TC 的指令在 ZDO 层，不是 NWK 单播 Leave）。
2. **TC 踢人指令 = Mgmt Leave Req（ZDP 0x0034），可见**！第二波踢人前 TC 发 Mgmt Leave Req ×12
   （t=1785138818.0-19.4）与设备广播 Leave ×3（t=1785138818.4-19.4）交织。
   ⚠️ **自审修正 (v1.2)**：v1.0/v1.1 断言 "TC 指令帧未被 sniffer 捕获" 是**错误结论**——
   首次分析只解析了 APS 0x07，未解析 ZDP 0x0034，把 "没解析" 误当成 "抓不到"。
3. **第一波无指令帧可见**（t=1785138804.4，最早 Mgmt Leave Req 是 t=1785138818.0）——
   指令帧可能丢失/盲区，或设备自行离网 → 该形态对应 **R2c（中置信）**。
4. **与 L1-3-B2 区分**：0xCBEB 无 TCLK 验证失败痕迹（无 tclk/verify/confirm 上下文），排除 B2。
5. **检测器判定**：`leave_question` → L1-4_HIT (R2b 高)；`1-标准入网抓包-2` (0x2951) → HEALTHY (负例)；
   `中继入网抓包(1)` → 838D L1-3 B2-LOOP 命中（无回归），且 **R2b 发现同素材 TC 踢 0x8A41/0xF67F
   （Mgmt Leave Req ×3 各）——v1.1 检测器漏报的 TC 踢人活动**。

### 示例 B2：（待素材）规则 R2a — 运营期踢人（0x07 显式）

**条件**：0x07 Remove Device 出现 + 目标已入网（Announce/TransportKey 在 0x07 之前）。
**候选素材**：需复现（TC 应用层显式移除，如网关管理页"删除设备"操作）。

### 示例 C：（待补）规则 R3 — 静默拒绝

**条件**：Assoc 成功 + 无 0x07 + 无 0x05(NWK) + 无 Announce + 设备消失（与 L1-3-A1 双报）。
**候选素材**：需复现（TC 配置 ignore 策略 / well-known key rejoin 静默拒）。
