# U23 — 拓扑页大包加载性能 (导入后首次进页 ~20s 且拖垮整个后端)

**What to build:** 把拓扑页在**大包导入后首次打开**的时间从 ~20s 降到可控 (<2s), 并消除
"计算期间整个后端被阻塞"的现象 (其它页面/轮询一起卡住 = 用户说的"卡顿")。

**Blocked by:** None | **Status:** ready-for-agent (未认领)

**Type:** task | **性能 (P1)**

**来源**: 2026-09-21/22 用户反馈 "导入包完后, 如果包比较大, 在这个拓扑页面下, 会加载比较久,
导致看起来卡顿"。属拓扑页整体梳理 (docs/topology_page_review.md) 的 P1 项。

## 实测 (2026-09-22, 素材 = 81MB / 1,738,481 帧 / 主 PAN 21 节点)

测量方式: CDP 冷启动 (导入后首次访问, 服务端缓存为空) + 页面内 fetch/XHR 计时钩子
(`.scratch/verification/u21-topo/u21_perf.mjs`)。

| 环节 | 实测 | 说明 |
|------|------|------|
| 页面壳 (DOMContentLoaded/load) | **0.45s / 0.51s** | 正常 |
| **`/api/topology/events` (冷)** | **19.8s** (首次含 timeline 构建) / **12.7s** (仅拓扑重算, 换 pan key 破缓存复现) | **瓶颈** |
| 首屏 (导航 → 图出现节点) | **20.7s** | = 上面的请求 |
| `/api/import/status` (**与 events 并发**) | **19.8s** (原本 75ms) | **阻塞铁证**: CPU 计算占满 → 同一时刻其它请求全排队 |
| `/api/topology/events` (热) | 0.53s / **5.1MB** payload | 仍有优化空间 |
| 前端渲染/交互 (布局应用) | **2~3ms/次** (拖游标 5 帧共 16ms) | 前端**不是**瓶颈 |
| 切布局 (列式/自由/放射) | 布局计算 2~4ms | 同上 |

## 根因 (代码级)

1. **events 端点 8 遍全量扫描** (纯 Python, 173 万帧 ×8):
   `_ensure_events_timeline` → `_build_phase3_supplements` → `derive_topology` ×2 →
   `_link_evidence_parent` → seen/member 统计 → `_enrich_nodes{_node_stats + _behavior_map +
   _link_evidence_parent(**重复调用**) + _online_map}` → `_all_link_segments`。
2. **payload 5.1MB**: `link_snapshots` 段数极多 (实测该素材 14441 parent 段 + 690 route 段),
   同一节点的相邻同签名段 (30s 窗切分, 反复 down/rr 交替) 未合并 → 传输+JSON.parse 也是热请求 0.53s 的主因。
3. **计算占满单进程** → 事件循环被阻塞 (FastAPI async 里跑 CPU 密集同步代码) → 其它请求排到 19.8s。
4. 前端无骨架/进度: 用户看到的是"点了没反应", 加剧"卡顿"感受。

## 方案 (按收益排序, 待认领时定细则)

| # | 方案 | 预期 | 代价/风险 |
|---|------|------|----------|
| 1 | **导入时预计算 + 持久化**: 拓扑页请求的永远是**全量无时间窗** (游标在前端过滤) → 可在导入任务里对主 PAN 预生成 events 结果并落盘, 页面请求直接命中 | 首屏 **20.7s → <1s**; 且不再有 CPU 突发 | 预计算结果需与后续代码版本兼容 (加版本戳/失效重建); 内存/磁盘占用 |
| 2 | **合并全量扫描**: behavior + 链路证据 + online + segments + 成员统计 合并为 1~2 遍 (per-node accumulator) | 冷算 13s → **~2-4s** | 中; 需逐字段对账 (P1 契约回归) |
| 3 | **payload 瘦身**: 相邻同签名段合并 + 大数组用紧凑表示 (或前端按需拉取) | 5.1MB → **<1MB**; 热请求 0.53s → ~0.15s | 低; 必须保证 link_snapshots 时刻语义不变 |
| 4 | **重活挪出事件循环**: `run_in_threadpool` / ProcessPool (参考 P3 的 ProcessPoolExecutor) | 其它端点不再被拖 | 低-中; 注意 frozen 需 freeze_support (T2 坑) |
| 5 | **前端骨架 + 进度**: 先渲染侧栏/空态 + "正在计算拓扑 (大包约需 Ns)" | 感知改善 | 低 |

推荐组合: **1 + 3 + 5** (一次性解决首屏与阻塞), 2 作为长期优化。

## 验证标准

1. 大包 (173 万帧) 导入后**首次**打开拓扑页: 首屏 < 2s; `events` 冷请求 < 2s (或命中预计算)。
2. **并发不阻塞**: events 计算进行时, `/api/import/status` / `/api/packets/types` 延迟 < 200ms。
3. **语义不回归**: link_snapshots 分段语义逐位一致 (时刻游标链路变化、链路历史面板、聚焦时间轴
   的段数与切换点不变) — 与 `u21_perf.mjs` + 链路历史对账脚本一起跑。
4. payload < 1.5MB; 热请求 < 0.3s。
5. 小包 (8千帧) 不受影响 (首屏 < 1s)。
6. 现有拓扑功能 (排布/聚合/时刻游标/图例/面板) 无回归 — 复用 U21 的 CDP 断言集。

## 风险 / 开放问题

- **预计算的适用边界**: 目前页面只请求全量 (S.topoT0/T1 来自时间线跳转时也会传 t0/t1! 见 loadData
  的 t0/t1 参数) → 需要确认所有调用路径; 若含时间窗请求, 预计算只能覆盖"全量"这一种, 其余仍走计算。
- 段合并可能改变前端"链路历史/时间轴"的段边界显示 → 必须逐素材对账 (U13/S3 的验证脚本可复用)。
- 大包的**导入耗时本身** (~10 min) 不在本 ticket 范围 (P3 已优化解析, 但 173 万帧仍需时间);
  用户感知的"导入后首次进页慢"才是本 ticket 目标。
