# 嵌入式设计需求锐化

在编写代码之前，对嵌入式系统或 Linux 驱动设计进行无情的结构化问答。读取项目知识图谱，然后遍历结构化决策树——一次一个问题——暴露未声明的假设和隐藏的复杂性。

**前置条件**：必须存在由 `/scan-embedded-project` 生成的 `PROJECT-KNOWLEDGE-GRAPH.md`。如果不存在，提示用户先运行扫描——没有图谱的问答是盲目的。

## 问答纪律

- **一次只问一个问题**。绝对不要批量提问。
- 每个问题包含**推荐答案**。
- 从代码库和知识图谱中探索**事实**；只把**决策**交给用户。
- 用户确认共享理解之后再行动。
- 术语和决策确定后，更新 `CONTEXT.md` 并创建 ADR（委派给 `/domain-modeling`）。

## 方向检测

开始时读取 `PROJECT-KNOWLEDGE-GRAPH.md` 以确定走哪棵决策树：

| 如果工程有... | 走这棵树 |
|---|---|
| Linux 内核构建系统、Device Tree、`struct platform_driver` | **方向 A：Linux 驱动** |
| RTOS 或裸机、`main()` 入口、启动文件、ISR 向量 | **方向 B：嵌入式 / 裸机** |
| 两者都有（如嵌入式 Linux BSP） | 两棵树都走，从用户问题所属的方向开始 |

## 方向 A：Linux 驱动开发

Linux 驱动设计决策树，共 **7 层**。遍历用户设计问题适用的每一层。用户明确排除的层跳过。

### 第 A1 层 — 设备模型

内核设备模型中你的设备处于什么位置？

**1. 总线挂载**
- 设备挂载在哪个总线上？（platform / I2C / SPI / USB / PCI / MDIO / 其他）
- 设备发现机制？（Device Tree 静态描述 / ACPI / USB 枚举 / I2C device table / 手动 `modprobe`）
- 已有子系统是否已覆盖此类设备？（传感器用 IIO / 输入设备用 HID / 音频用 ALSA / 视频用 V4L2 / 串口用 TTY / 网卡用 network device）
  → 如果是，为什么不复用？如果否，说明新建子系统接口的理由。

**2. 暴露给用户空间的设备节点**
- `/dev/` 下出现哪些节点？（每个设备一个？每个功能一个？）
- `/sys/` 下出现什么？（class 属性？device 属性？）
- `/sys/kernel/debug/` 下出现什么？（调试状态 dump？）
- `/proc/` 下出现什么？（新代码中极少使用——如果使用需说明理由）

### 第 A2 层 — 内存与地址空间

驱动如何访问硬件内存？

**1. MMIO 区域**
- 基地址和大小？（从 Device Tree `reg` 属性或 ACPI _CRS 获取）
- 对齐要求？（`ioremap` 需要页对齐，或用 `devm_ioremap_resource`）
- 是否有多个内存区域？（BAR0 + BAR1，或不同的寄存器组）

**2. DMA 缓冲区**
- 是否需要 DMA？（streaming 用 `dma_map_single`，coherent 用 `dma_alloc_coherent`）
- DMA 传输大小和对齐约束是什么？
- 缓存一致性——平台是否保证，还是需要手动管理？（ARM：DMA 前后必须 clean/invalidate 缓存行）
- IOMMU/SMMU 存在吗？是否影响 DMA 地址转换？

**3. 用户空间内存访问**
- 用户空间是否需要直接访问设备内存？（通过 `remap_pfn_range` 或 `vm_insert_page` 做 mmap）
- 如果 mmap：缓存模型是什么？（write-combine / uncached / write-back）
- 用户空间获得什么权限？（只读 / 读写 / mmap COW 语义）

### 第 A3 层 — 中断与并发

并发模型是什么？

**1. 中断拓扑**
- 单中断线还是多中断线？
- 边沿触发还是电平触发？（电平触发处理不当 = 中断风暴）
- 中断是否共享？（`IRQF_SHARED` — 要求 irq handler 检查"是不是我的设备产生了中断？"）
- 中断是否需要线程化？（`request_threaded_irq` — hardirq 做最小处理，threaded fn 做其余工作）

**2. 中断处理拆分**
- hardirq 上下文中必须做什么？（ack 中断、清除中断源、调度下半部）
- 什么在 threaded handler / tasklet / workqueue 中运行？
- hardirq 的最长执行时间是多少？（每一微秒都阻塞此优先级的所有其他中断）

**3. 共享数据保护**
- ISR 和进程上下文之间共享什么数据？→ `spin_lock_irqsave`
- 两个进程上下文路径之间共享什么数据？→ `mutex`（可睡眠）或 `spin_lock`（不可睡眠）
- 两个不同优先级的不同 ISR 之间共享什么数据？→ `spin_lock` 配合适当的 IRQ 屏蔽
- 是否存在优先级反转风险？（低优先级线程持有高优先级 ISR 的线程化处理函数所需的 mutex）

**4. 锁排序**
- 定义锁层级：如果锁 A 在所有地方都在锁 B 之前获取，显式声明这一点
- 是否存在顺序可能反转的路径？（子系统回调持有锁 X，你的代码尝试获取锁 Y——这安全吗？）

### 第 A4 层 — 用户空间接口

内核与用户空间之间的契约：

**1. 控制路径**
- ioctl：哪些命令号？如何编码？（`_IO`/`_IOW`/`_IOR`/`_IOWR` 宏——大小和方向必须正确）
- sysfs：哪些属性？每个文件一个值，优先人类可读
- configfs：是否需要从用户空间创建复杂对象？
- netlink：是否需要多播事件或高容量结构化数据？

**2. 数据路径**
- read/write：流式数据？块大小假设？
- mmap：高带宽数据的零拷贝？（共享内存中的环形缓冲区）
- splice/sendfile：设备是否支持页对齐 DMA 直接到/从用户空间页面？

**3. 事件通知**
- poll/epoll：什么条件唤醒等待者？（数据可用 / 错误 / 挂断）
- uevent：用于设备热插拔或状态变化
- signal：仅用于进程导向事件（SIGIO），且仅在有充分理由时

**4. 向后兼容性**
- 这是新接口还是扩展现有接口？
- 如果是扩展：旧的用户空间二进制程序是否仍能工作？（ioctl 大小检查、sysfs 文件重命名）
- 如果是新建：ABI 从第一天起就是稳定的，还是标记为 staging/CONFIG_STAGING？

### 第 A5 层 — 电源管理

电源状态机：

**1. 系统休眠**
- 支持哪些休眠状态？（freeze / standby / mem / disk）
- 休眠时设备做什么？（断电？保留状态？恢复时复位？）
- 是否必须保存/恢复寄存器，还是设备保留它们？
- 休眠期间进行中的 DMA/IRQ 怎么办？（排空队列？中止？）

**2. 运行时 PM**
- 设备何时自动休眠？（空闲 N 毫秒后）
- 自动休眠的唤醒延迟是多少？（对使用场景可接受吗？）
- 什么事件唤醒设备？（用户空间访问 / IRQ / 定时器）
- 是否需要在每个入口点配对 `pm_runtime_get_sync`/`pm_runtime_put`？

**3. 时钟和 regulator 管理**
- 设备需要哪些时钟？（总线时钟 + 功能时钟 + PLL）
- 需要哪些 regulator？（核心电压 + I/O 电压 + 模拟电源）
- 使能/禁用的顺序约束？（"功能时钟必须在复位解除之前稳定"）
- 是否使用 `devm_clk_get` 在 probe 失败/remove 时自动清理？

### 第 A6 层 — 错误处理与恢复

硬件出问题时怎么办？

**1. 错误分类**
- 可恢复错误：（超时 → 重试 / CRC 错误 → 请求重传 / FIFO 溢出 → 刷新）
- 需要设备复位：（DMA 引擎挂死 / 外设状态机卡住 / 协议死锁）
- 需要总线复位：（I2C 总线锁低 / SPI 从机无响应 / USB 端口复位）
- 系统级致命错误：（电源轨故障 / 时钟源丢失 / 不可纠正的 ECC 错误）

**2. 超时策略**
- 每个忙等待或完成等待都有超时——值基于什么？（数据手册最大延迟 + 余量，不是"随便选个数"）
- 超时时怎么办？（重试 N 次 → 升级 → 向用户空间报告错误）
- 是否有硬件看门狗作为软件超时的后盾？

**3. 复位后的状态恢复**
- 设备复位后：重新初始化寄存器，重新排队待处理的 I/O，通知用户空间
- 无法恢复的状态：什么会丢失？用户空间必须重新发送什么？

**4. 错误上报**
- 内核日志：`dev_err`/`dev_warn`——带足够的调试上下文（寄存器 dump？请求信息？）
- ftrace/tracepoint：用于对时序关键的错误路径（不能等 printk）
- devcoredump：用于在致命错误时捕获设备状态供离线分析
- 用户空间通知：应用程序看到什么？（read/write 返回 errno？poll POLLERR？uevent？）

### 第 A7 层 — 测试与可调试性

如何验证驱动正常工作？

**1. 无硬件开发**
- 此类设备是否有 QEMU 仿真可用？
- 能否在总线层模拟硬件？（I2C 从机模拟器 / SPI 环回）
- 如果无法仿真：所需的最小硬件是什么？

**2. 调试手段**
- debugfs 条目：哪些内部状态值得暴露？（寄存器 dump / 描述符环状态 / 统计计数器 / 最近 N 个错误）
- ftrace tracepoint：打在哪里？（ISR 入口/出口、DMA 完成、错误路径）
- 动态调试（`pr_debug`/`dev_dbg`）：运行时可控，无需重新编译

**3. 测试策略**
- 单元测试：kunit 用于算法、数据结构、状态机（无需硬件）
- 集成测试：总线级模拟或 QEMU + 真实驱动代码
- 硬件在环：自动测试夹具操作真实设备
- 已知 errata workaround：如何测试？

**4. 压力测试**
- 多线程并发 open/close/ioctl
- 快速设备插拔（如果支持热插拔）
- 内存压力下的 DMA（系统 DMA 可用页面不足）
- 最大吞吐量持续 N 小时

## 方向 B：嵌入式 / 裸机开发

嵌入式系统设计决策树，共 **6 层**。遍历适用的每一层。

### 第 B1 层 — 启动与内存

从上电到 `main()`：

**1. 启动序列**
- Bootloader：`main()` 之前运行什么？（厂商 ROM boot → 一级 boot → 二级 boot → app）
- Flash 分区布局：画出 boot / app / storage / OTA 镜像 A / OTA 镜像 B / NVRAM
- 启动参数：bootloader 向 app 传递什么？（栈指针？RAM 大小？固件版本？）
- 安全启动：启动镜像是否签名？公钥存储在哪里？验证失败怎么办？

**2. 内存布局（从链接脚本）**
- 栈：大小？在 RAM 顶部还是专用区域？MSP vs PSP（用于 OS 任务）？
- 堆：大小？分配策略？（TLSF / buddy / dl_malloc / 仅静态池 / 无堆）
- .data / .bss / .rodata：是否在链接脚本规定的位置？
- 特殊段：校准数据 / 序列号 / 安全密钥 / 出厂配置
- 栈溢出检测：MPU 保护区域？软件 watermark？什么都没有？

**3. 堆策略**
- 是否允许动态分配？如果允许，何时？（仅初始化时 / 始终 / 启动后永远不允许）
- 碎片风险：最坏情况碎片及其后果？（设备变砖？优雅降级？）
- 分配失败处理：`malloc` 返回 NULL 时怎么办？

### 第 B2 层 — 实时约束

实时性契约：

**1. 延迟要求**
- 硬实时截止时间：从事件到响应的最坏延迟是多少？（硬件信号 → ISR 第一条指令 / ISR 入口 → 任务唤醒 / 任务唤醒 → 动作执行）
- 软实时："应在 X ms 以内，但偶尔超时可以接受"
- 吞吐量要求：持续数据速率（UART 1Mbaud / ADC 10ksps / BLE 2M PHY）

**2. 中断架构**
- 优先级分配：哪个 IRQ 获得哪个优先级？说明理由。
- 最大临界段长度：关中断的最长时间——以微秒为单位
- 嵌套中断：是否允许？如果允许，最大嵌套深度是多少？
- 尾链：是否依赖 NVIC 尾链行为？（Cortex-M 特有）

**3. 任务调度**
- 调度策略：抢占式 / 协作式 / 时间片轮转？
- 是否做过 Rate-Monotonic 分析？（每个任务在最坏相位下能否满足截止时间？）
- 优先级反转：识别每个互斥锁，以及低优先级任务是否能阻塞高优先级任务

**4. 定时器基础设施**
- Tick 频率：RTOS tick 频率是多少？（1ms？100µs？tickless？）
- 高分辨率定时器：需要吗？如何实现？（直接使用硬件定时器，而非 RTOS tick）
- 软件定时器 vs 硬件定时器：哪些定时器资源分配给哪些用途？

### 第 B3 层 — 外设与 HAL 设计

硬件抽象：

**1. HAL 设计**
- 抽象层位置：硬件相关和硬件无关之间的界限在哪里？（画出边界——哪些 .c 文件允许 `#include` 厂商 HAL，哪些不允许？）
- HAL 接口：HAL 暴露什么？（init/read/write/ioctl/register_callback？）
- 多平台支持：HAL 是为当前 MCU 设计，还是足够抽象以支持未来移植？
- HAL 测试：无硬件时如何测试 HAL 代码？（仅编译？QEMU？Renode？）

**2. 外设分配**
- 定时器分配：有多少硬件定时器？哪个定时器服务哪个功能？（系统 tick / 协议栈时序 / PWM / 输入捕获 / 软件定时器支撑）
- DMA 通道分配：哪些通道分配给哪些外设？同一 DMA 引擎是否有竞争？
- 共享 SPI/I2C 总线：哪些设备共享同一总线？仲裁机制是什么？
- 引脚冲突：是否有 GPIO 服务两个主设备？（复用功能冲突）

**3. 时钟树**
- 时钟源：HSI / HSE / PLL / LSI / LSE——各自用于什么？
- 时钟分配：画出树：源 → 预分频器 → 外设时钟 → 最大频率
- 动态时钟调节：是否对未使用的外设进行时钟门控？何时？如何？

**4. 寄存器访问模式**
- 直接写寄存器 vs HAL 函数 vs 生成代码（CMSIS / svd2rust）
- 读-修改-写安全性：什么时候 RMW 序列是原子的 vs 中断不安全的？
- 写入顺序：是否存在必须按特定顺序写入且需要延时的寄存器？
- 保留位：你是向保留位写零，还是意外地设置了它们？

### 第 B4 层 — 电源管理

功耗预算：

**1. 功耗模式**
- 列出每种模式：run / sleep / deep sleep / standby / shutdown
- 进入条件：什么触发进入每种模式？
- 退出条件：什么从每种模式唤醒？（GPIO / RTC / LPUART / BLE 无线电 / 复位）
- 状态保留：每种模式保留什么？（RAM 保持？寄存器状态？GPIO 输出电平？）

**2. 唤醒延迟**
- 每种低功耗模式的唤醒时间是多少？
- 唤醒延迟对应用可接受吗？（BLE 连接间隔有硬性截止时间）
- 唤醒期间待处理的中断怎么办？它们以什么顺序触发？

**3. 外设电源**
- 哪些外设是常开的 vs 有条件供电的？
- 电源域分组：如果你门控时钟 X，哪些外设一起掉电？
- 模拟 vs 数字电源：上电时顺序是否正确？

**4. 功耗测量计划**
- 如何测量实际功耗？（电流探头 + 示波器 / Power Monitor / 万用表粗测）
- 每种功耗模式下的预期电流是多少？
- 在什么场景下测量？（空闲 / 主动发送 / 主动接收 / 连接休眠）

### 第 B5 层 — 无线协议栈集成

协议栈如何融入系统：

**1. 协议栈集成模式**
- SoC 模式（协议栈与应用在同一 MCU 上运行）还是 NCP 模式（协议栈在独立芯片上运行）？
- 如果是 SoC：协议栈消耗多少 flash/RAM？应用还剩多少？
- 如果是 NCP：主机接口是什么？（UART / SPI）协议是什么？（HCI / EZSP / AT 命令）
- 协议栈的实时要求：它对应用施加了什么截止时间？

**2. 协议栈资源消耗**
- 定时器：协议栈需要多少软件定时器？
- 无线访问：无线占空比是多少？无线何时对应用不可用？
- 临界段：协议栈关中断多长时间？是否会饿死你的 ISR？
- 缓冲区池：可以排队多少数据包？溢出时怎么办？

**3. 多协议共存**
- 同一无线电上是否有多个协议？（BLE + Zigbee / BLE + Thread）
- 调度：时分复用？基于优先级的抢占？协作让出？
- 天线共享：外部开关切换的共享天线？片上合并？
- 已知的交互 bug：厂商对共存限制说了什么？

**4. 安全**
- 密钥存储：在哪里？（OTP / 安全元件 / 加密 flash / 明文 flash——明确说明）
- 密钥注入：出厂时？配对时？空中？
- OTA 升级：双槽 / 带恢复的单槽 / 加密镜像 / 签名镜像
- 调试端口：生产时锁定？解锁程序？重放攻击防护？

### 第 B6 层 — 故障诊断与现场恢复

设备在现场出问题时：

**1. 故障处理函数**
- HardFault / MemManage / BusFault / UsageFault 处理函数：具体做什么？（捕获压栈的 PC/LR/SP → 保存到持久存储 → 复位？还是只复位？）
- Assert 行为：断言失败时发生什么？（LED 闪烁的死循环？保存上下文后复位？无——发布版中 assert 被编译移除？）
- 看门狗：窗口看门狗还是独立看门狗？喂狗点在哪里？任务挂死时怎么办？

**2. 崩溃取证**
- 崩溃 dump：捕获什么？（寄存器快照 / 栈内容 / 最近日志 / 复位原因）
- 存储：崩溃 dump 保存在哪里？（专用 flash 区域 / 外部 EEPROM / 软复位后仍保留的 RAM）
- 提取：开发者如何提取崩溃 dump？（调试器 / CLI 命令 / 自动上传）
- 符号化：是否有工具将崩溃 dump 地址转换为函数名？

**3. 远程诊断（用于已部署设备）**
- 无需物理接触可以获取什么信息？
- 能否通过 OTA 加载诊断固件？
- 持续采集什么遥测数据？（运行时间 / 复位次数 / RSSI / 错误计数 / 电池电压）

**4. 恢复策略**
- 崩溃后：正常重启？启动到安全模式？等待 OTA 恢复镜像？
- 恢复出厂设置：如何触发？什么状态会保留？
- 防变砖：什么保护措施防止 OTA 升级失败导致设备不可恢复？

当用户确认共享理解：

1. 所有已解决的术语 → 更新 `CONTEXT.md`（通过 `/domain-modeling`）
2. 难以逆转 + 缺少上下文会令人困惑 + 存在真实权衡的决策 → 写 ADR（通过 `/domain-modeling`）
3. 总结每层做出的决策——此摘要直接输入 `/to-driver-spec`
