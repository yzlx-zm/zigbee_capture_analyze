## 关键能力 (已验证)

- APS 命令 ID 提取 (0x05/0x08/0x0F/0x10) + key_type — 手动字节解析
- NWK Key / TCLK 明文提取; VerifyKey 16B = keyed_hash(TCLK,3) 破解
- Network Status (0x0B) / Leave 标志 / Remove Device target / Update Device status
- 默认 ZigBeeAlliance09 key 兜底解密 (0x20/0x38 误读根源已修)
- 导入进度回调 (progress_cb)

## 已知问题/风险

| 问题 | 影响 | 备注 |
|------|------|------|
| **双路径字段契约不一致** | cubx/pcap 同素材解析结果差异 → 检测器误判 | 0x20/0x38 教训; nwk_cmd_id 曾缺 |
| **无素材回归测试** | 改解析器靠人工验证, 回归风险高 | 每次改 cubx_reader 都手工跑素材 |
| **大包性能** | 26-260MB cubx 导入慢 (进度条卡 0 已修, 性能待优化) | 07240934_26.cubx 等 |
| **解密覆盖有限** | 部分帧解不出 (缺 key 场景) → 字段缺失 | 依赖 key_store + 默认 key |
| **字段缺口靠检测器驱动** | 检测器要新字段 → 解析器扩展 (被动) | ticket 05 "解析器字段扩展" 模式 |

## 拆分维度 (解析器工程 tickets)

### 按能力
- **P1 双路径字段契约对齐**: cubx vs tshark 输出字段全集盘点 + 对齐测试 (防 0x20/0x38 复发)
- **P2 素材回归测试体系**: 已知素材 (健康/故障) 字段快照 + 自动回归 (改解析器必跑)
- **P3 大包性能优化**: 260MB cubx 导入提速 (索引/惰性解析/内存)
- **P4 解密覆盖扩展**: 更多 key 类型/哈希变体/失败原因可观测
- **P5 字段缺口工单流**: 检测器需求的字段 → 解析器扩展的规范化流程 (与检测工程联动)

### 按依赖关系
- 检测工程 (L1-L7) 依赖解析器字段 → 检测 ticket 发现缺口 → P5 建解析器 ticket
- UI 工程依赖解析器输出字段 → UI 会话遇解析器问题 → 建解析器 ticket (不阻塞 UI 会话)

## 与上下游工程的关系

```
抓包数据 (cubx/pcap)
  → [解析器工程] 解密+字段提取 → dict
    → [检测工程] L1-L7 检测器 → 诊断卡片
    → [UI 工程] 拓扑/时间线/节点/诊断 展示
```

**解析器是地基**: 检测器和 UI 都依赖它的输出。字段缺口应走 P5 工单流, 避免各工程各自为政改解析器。
