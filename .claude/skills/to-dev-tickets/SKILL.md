# 生成开发工单

将规范或设计拆分为**追踪弹工单**——每个工单是贯穿嵌入式全栈的垂直切片，每个工单声明其阻塞边。

## 嵌入式"全栈"

一个垂直切片必须穿透每个适用的层：

```
硬件抽象 → 驱动核心 → OS 适配 → 应用逻辑 → 测试
```

一个合格的切片完成后是**可独立演示或验证的**。

## 流程

### 1. 收集上下文

从对话、驱动规范或用户传递的引用中获取信息。读取 `PROJECT-KNOWLEDGE-GRAPH.md` 获取架构上下文。

### 2. 起草垂直切片

规则：
- 每个切片是贯穿所有层的**窄但完整**的路径
- 完成切片 = 可独立验证（烧录并测试）
- 大小适合单个 AI 会话（不要太大）
- 预重构（让变更变容易）放在最前面

**好的（垂直切片）：**
```
工单："通过 I2C 读取温度寄存器并通过调试串口上报"
├── HAL：    sensor_ops 结构体（init/read/power）
├── 驱动：    I2C 寄存器读取 + CRC 校验
├── OS：     封装为 FreeRTOS 任务
├── 应用：   原始值 → 毫摄氏度转换，格式化输出
└── 测试：   I2C mock 注入 + 真实传感器验证
```

**坏的（水平切片——拒绝）：**
```
❌ "实现所有 I2C 驱动"     → 水平切片，没有用户可见行为
❌ "写所有模块的 init 函数" → 又一个水平切片
```

**宽泛重构**是例外。如果变更在整个代码库中都有影响范围，使用扩展-收缩模式。

### 3. 向用户确认

以编号列表呈现：

```
#1 <标题>
阻塞于：无——可立即开始
交付：<此工单实现的端到端行为>

#2 <标题>
阻塞于：#1
交付：<行为>
```

询问：
- 粒度合适吗？
- 阻塞边正确吗？
- 是否需要合并或进一步拆分？

### 4. 发布

在 `.scratch/<功能简称>/issues/<编号>-<简称>.md` 下按依赖顺序每工单写一个文件。

### 工单模板

```markdown
# <编号> — <工单标题>

**要构建的内容**：此工单实现的端到端行为，从用户/开发者视角描述。

**阻塞于**：<工单编号/标题，或"无——可立即开始">

**需要硬件**：<开发板、调试器、仪器>

**烧录命令**：<jlink / openocd / dfu-util 命令行>

**验证方式**：<如何确认它工作——逻辑分析仪？串口输出？LED 模式？>

**状态**：ready

- [ ] 验收标准 1
- [ ] 验收标准 2
```
