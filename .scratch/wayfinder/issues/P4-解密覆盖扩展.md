## Resolution (2026-08-10, 含自审修正)

**素材实证发现 (自审修正两个错误推断)**:
- 中继包全量安全帧 key_type 分布 (scapy 原生 ZigbeeSecurityHeader 实测):
  **{0: 4147 (99.98%), 3: 1}** — 几乎所有安全帧是 key_type=0 (Data Key / link key 加密)
- 解密成功 1722 帧 = ZigBeeAlliance09 (默认 TC link key) 解开;失败 2428 帧 =
  **设备唯一 TC link key 加密** (网关入网时分配) — key 不在 key_store, 素材内不可判定
- ❌ 撤回: 早期手写 aux 偏移统计 {1:609,0:623,2:614,3:582} 全错 (NWK 头变长偏移
  非 7);"load hash selector 0x02 素材实证" 无实证 (key_type=2/3 素材仅 1 帧)

**实施**:
1. **解密失败原因可观测** (核心):
   - cubx_reader: 新字段 `sec_key_type` (aux header bits1-2, 成功/失败帧都填) +
     `decrypt_note` (None=成功 / missing_key=候选空 / mic_fail=有候选不匹配 /
     parse_error=安全头解析异常)
   - tshark 路径对齐: `sec_key_type` 从 `zbee.sec.key_id` (tshark -G fields 确认);
     decrypt_note 占位 None (pcap 路径 tshark 内部解密, 原因不可从输出判定 — 诚实占位)
2. **VerifyKey (key_type=4) 候选**: `_security_candidates` 加 selector 0x03
   keyed_hash (协议级补全; 素材无 key_type=4 帧, 待素材验证 — 不标实证)
3. **校验报告增强**: parser_verify decrypt_health 按 decrypt_note 分类 —
   中继包现在显示: "2428/4150 未解密 (58.5%) [疑似缺 key] [mic_fail:2426, parse_error:2]"

**回归**: p2 快照 --update (新字段有意变更) + 4/4; p1_regression 15/15;
test_parser_verify 12/12

**素材侧机会**: 提供中继设备 (838D 等) 的 TC link key → key_store 添加 →
58.5% 失败帧可解, L3-1/L3-5 计数可能变化
