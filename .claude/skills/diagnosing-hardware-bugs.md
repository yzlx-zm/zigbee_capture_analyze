# 硬件 Bug 诊断

一套针对困难嵌入式 bug（硬件、固件和协议层面）的 6 阶段调试纪律。**仅在显式说明理由时才跳过阶段。**

探索代码库时，阅读 `PROJECT-KNOWLEDGE-GRAPH.md` 和 `CONTEXT.md`（如果存在）以理解硬件和模块格局。

## 阶段 1 — 构建反馈循环

**这就是核心技能。** 其余都是机械的。如果你对此 bug 有了一个**紧**的通过/失败信号，你就能找到原因。如果没有，看再多代码也救不了你。

在此投入不成比例的精力。**要有侵略性。要有创造力。拒绝放弃。**

### 嵌入式反馈循环谱系

按大致顺序尝试（最快/最可靠优先）：

**S 级（毫秒级）**
1. **JTAG/SWD 断点 + 观察点**
   → 在可疑变量或寄存器地址上设置硬件观察点
   → Bug 触发 → CPU 停止 → dump 调用栈、局部变量、寄存器
   → Cortex-M：通常可用 4-6 个硬件断点

**A 级（秒级搭建，毫秒级循环）**
2. **逻辑分析仪 + GPIO 翻转**
   → 在关键代码路径插入 `gpio_set(DEBUG_PIN)`/`gpio_clear(DEBUG_PIN)`
   → 逻辑分析仪捕获 ISR、任务、DMA 之间的时序关系
   → 理想用途：中断延迟测量、协议时序验证、竞态条件
   → 引脚翻转开销：约 2-5 个 CPU 周期——对大多数调试可忽略不计

3. **串口调试输出（优先速度）**
   → SEGGER RTT（200KB/s，非阻塞）> SWO/ITM > 缓冲 UART > 阻塞 UART
   → 为每条调试输出打标签：`[DEBUG-a4f2] <消息>`
   → 避免：在 ISR 中 printf、低波特率未缓冲 UART

**B 级（分钟级）**
4. **寄存器快照对比**
   → 在故障前后各 dump 一次外设寄存器组
   → Diff 找出哪些位意外变化了
   → 理想用途：外设配置错误、时钟树问题、DMA 状态损坏

5. **HardFault 分析器**
   → 从压栈的 PC/LR/SP 通过符号表反解为函数名
   → 解码 CFSR/UFSR/MMFSR/BFSR 确定故障类型
   → ARM：`arm-none-eabi-addr2line -e firmware.elf <PC>` 反解崩溃地址
   → RISC-V：`mcause` 寄存器告知 trap 原因

6. **电流波形分析**
   → 示波器 + 电源轨电流探头
   → 捕获故障时刻的功耗特征
   → 理想用途：电源相关 bug、外设未正确休眠、意外的功耗尖峰

**C 级（分钟到小时级）**
7. **二分法——硬件隔离**
   → 物理断开子模块，每次移除后重新测试
   → "当我禁用传感器 X / 断开板子 Y 时，bug 还存在吗？"

8. **二分法——固件版本（在硬件上 `git bisect`）**
   → 需要：自动化烧录 + 测试夹具
   → 每步：烧录、运行测试、报告好/坏

9. **HITL（人在回路）脚本**
   → 最后手段。脚本驱动操作员按结构化步骤操作
   → 输出按步骤结构化为通过/失败

**D 级（小时到天级）**
10. **远程诊断（已部署设备）**
    → 设备上传崩溃 dump → 离线符号分析
    → 远程日志提取/遥测仪表板
    → OTA 诊断固件增强日志

### 收紧循环

一旦有了**一个**循环，改进它：

- **更快？** 缓存初始化、跳过无关启动、缩小测试范围
- **更清晰的信号？** 断言具体症状，而不是"设备没崩溃"
- **更确定？** 固定时间、种子 RNG、固定电压、屏蔽 EMI

30 秒的不可靠循环几乎和没有循环一样糟糕；2 秒的确定性循环是超能力。

### 非确定性 Bug

目标不是干净的复现，而是**更高的复现率**：

- 循环触发 100 次或 1000 次
- 加压力：升高/降低电压、升高温度、注入 RF 噪声、并发运行任务
- 缩小时间窗口：在操作间加入小延迟以找到竞态甜区
- 50% 概率的不可靠 bug 可调试；1% 不可以——持续提高复现率

### 当确实无法构建循环时

**停下来并明确说明。** 列出你尝试的方法。向用户要求：
- 访问能复现问题的环境
- 捕获的物证（逻辑分析仪波形、寄存器 dump、核心 dump、串口日志、屏幕录像）
- 在生产固件中添加临时诊断代码的权限

**没有循环，不要进入假设阶段。**

### 阶段 1 完成标准

一个能变红的紧循环：

- [ ] **能变红**：驱动实际的 bug 代码路径并断言**用户描述的具体症状**
- [ ] **确定性**：每次运行同样结果（不可靠 bug：高复现率）
- [ ] **足够快**：理想为秒级；5 分钟以内可接受；更慢需明确说明
- [ ] **Agent 可运行**（如果是自动化）或 **HITL 结构化**（如果涉及人工）

## 阶段 2 — 复现 + 最小化

运行循环。看它变红——bug 出现。

确认：
- [ ] 故障与**用户**描述的匹配——不是附近的其他故障
- [ ] 多次运行可复现（或不可靠 bug 的复现率足够高）
- [ ] 捕获了确切的症状供后续验证

### 最小化

将复现场景缩小到**仍能变红的最小场景**：

- 一次移除一个硬件模块，重新测试
- 注释掉代码路径，重新测试
- 减少输入数据大小，重新测试
- 简化配置，重新测试

**只保留对故障有影响的因素。** 当移除任何剩余元素都会使 bug 消失时完成。

---

## 阶段 3 — 假设

在测试**之前**生成 **3-5 个排序的假设**。单一假设会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**——陈述预测：

> "如果 X 是原因，那么改变 Y 会使 bug 消失 / 改变 Z 会使它恶化。"

嵌入式特有的假设维度：

| 维度 | 示例假设 |
|------|---------|
| 软件：并发 | "如果 `uart_tx_buf` 上的数据竞争是原因，那么在所有访问周围加自旋锁将使崩溃消失。" |
| 软件：内存 | "如果栈溢出是原因，那么将任务栈增加 256 字节将阻止崩溃。" |
| 软件：时序 | "如果 ISR 执行时间超过 BLE ISR 截止时间是原因，那么将处理移到低优先级任务将阻止 BLE 断连。" |
| 硬件：信号 | "如果电源噪声是原因，那么加 100µF 电容将消除 I2C NACK。" |
| 硬件：元件 | "如果晶振频率偏差是原因，那么换成已知好的晶振将修复 BLE 连接失败。" |
| 硬件 errata | "如果这匹配 errata ES-047，那么应用厂商的 workaround（寄存器写后插入 NOP）将修复。" |
| 协议：时序 | "如果协调器在 MAC 超时窗口之后发送 ACK，那么增加 `macAckWaitDuration` 2 个符号周期将阻止重传风暴。" |

**在测试前向用户展示排序列表。** 他们通常有能立即重排的知识。如果用户不在，不用等——按你的排序继续进行。

---

## 阶段 4 — 检测

每个探针必须映射到阶段 3 中的特定预测。**一次只改变一个变量。**

工具偏好（嵌入式重排）：

1. **硬件断点/观察点**——最精确，侵入性最小。一个断点胜过一百条日志。
2. **GPIO 翻转 + 逻辑分析仪**——不改变代码时序（对实时 bug 至关重要）
3. **单条标记输出**——`[DEBUG-xxxx]` 带最少格式
4. **决策点寄存器 dump**——用于外设状态异常
5. **绝对不要**"全量打印然后 grep"——在嵌入式上这是自找的拒绝服务攻击

### 标记规则

每个调试产物获得唯一前缀：`[DEBUG-a4f2]`。最后用一次 grep 清理。未标记的 instrumentation 存活；标记的 instrumentation 死亡。

### 性能分支

对于性能/时序 bug，日志会扭曲测量。替代方案：
- 用时序工具建立基线（GPIO 翻转用示波器/逻辑分析仪测量）
- 用零开销 instrumentation 做性能分析（ETM trace、Cortex-M 上的 DWT 周期计数器）
- 先测量，后修复

---

## 阶段 5 — 修复 + 回归测试

**在修复之前写回归测试**——但仅在存在正确接缝时。

嵌入式测试接缝，按优先级排序：

1. **HIL 测试**：自动测试夹具操作真实硬件
2. **HAL mock 单元测试**：为宿主机编译驱动代码，mock HAL 调用
3. **专用测试固件**：隔离 bug 路径的最小固件，可烧录验证
4. **文档化手动测试**：以上都不可行时，写精确的步骤供人工复现验证

如果**没有正确的接缝存在**，这本身就是发现。记录下来——架构阻止了此 bug 被锁定。标记给事后分析。

如果存在正确的接缝：
1. 将最小化的复现场景变成该接缝处的失败测试
2. 看它失败
3. 应用修复
4. 看它通过
5. 重新运行阶段 1 的反馈循环（原始未最小化场景）

---

## 阶段 6 — 清理 + 事后分析

声明完成前必须做的事：

- [ ] 原始复现场景不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录接缝缺失情况）
- [ ] 所有 `[DEBUG-xxxx]` instrumentation 已移除（在整个代码库 grep 前缀）
- [ ] GPIO 调试翻转已移除
- [ ] 一次性测试固件已归档或删除
- [ ] 正确的假设已写在 commit/PR 消息中

### 事后分析问题

修复后问：

1. **什么能预防此 bug？**（缺少 MPU 配置？看门狗喂太早/太频繁？硬件忙等待无超时？寄存器写入顺序未强制？）
2. **此 bug 是否需要硬件设计变更？** → 如果是，升级给硬件团队并附具体证据
3. **此 bug 是否暴露了无 workaround 的厂商 errata？** → 如果是，考虑更换硬件方案或架构级 workaround
4. **这需要写 ADR 吗？** → 如果修复涉及难以逆转的设计决策 → 通过 `/domain-modeling` 写 ADR
